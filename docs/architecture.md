# 超凡世界对战模拟器：架构设计

> 版本 v0.3（2026-10-05）· 全卡池完成：指定系列 516 张卡（含衍生物、纹章、信仰、特殊形态共 586 个有能力的卡牌定义）全部有脚本，任意两套合法卡组都能完整对战
> 配套文档：[规则摘要](rules-reference.md) · [卡池与数据源](card-pool.md)

## 0. 一句话目标

针对《影之诗：超凡世界》**指定系列（Rotation）**的几套固定卡组，做一个**规则准确、跑得快、可以复制和回放**的对战模拟器，在它上面依次搭建斩杀求解器、搜索型 AI，最后再接强化学习，用来当自己的陪练和复盘教练。

## 1. 目标与非目标

| 目标 | 说明 |
|---|---|
| 规则准确 | 以官方规则、官方词汇表和官方卡牌 Q&A 为准，每条规则都有测试 |
| 先做透再铺开 | 先做透 2 套卡组（M2），再铺开到指定系列全卡池（M2.5）；规则引擎本身是通用的 |
| 可复制、可回放 | `state.clone()` 能分支对局；种子加动作序列能完整复现一局 |
| 对 AI 友好 | 统一的 `legal_actions / apply / clone / observe / determinize` 接口 |
| 快 | 能支撑搜索和训练；早做性能分析（Jason 视频里的教训） |

**非目标**
- **不接入真实游戏客户端。** 用户协议禁止外部工具、机器人和逆向工程，详见 [card-pool.md §6](card-pool.md#6-法律与使用边界)。真实对局只用于人工复盘。
- **只做指定系列。** 无限制、无禁止、起始系列等赛制不在范围内；轮换后跟着卡池更新。
- **暂不做图形界面。** 先做命令行，以后再考虑网页。

## 2. 调研得出的设计约束

1. **卡池是封闭的。** 指定系列一共 515 张牌、56 个衍生物，没有任何"从全卡池随机生成"的效果，只有复制对手卡组或手牌里的牌（仍在两套卡组的范围内）。
   - 一局里可能出现的牌，就是"双方卡组 + 它们的衍生物"，词表是固定的。神经网络可以直接给每个 card_id 学一个嵌入向量，不需要理解卡面文字。
2. **官方数据只有数值是结构化的。** 官方 JSON 接口提供费用、身材、类型、职业、关联衍生物和 Q&A，**能力只有自然语言文本**。所以：
   - 数值和独立成行的关键词自动导入；
   - 能力逐张手写脚本。卡面文字里的 `<ev>`、`<sev>`、`<ridx>` 标记可以辅助切分。
3. **官方 Q&A 是现成的测试用例。** 数据库里有 120 张卡、共 165 条官方裁定，可以直接转成回归测试。
4. **规则本身决定了引擎骨架**（细节见规则摘要）：
   - 触发能力进入**先进先出队列**，结算中不会被打断，新触发排到队尾；
   - 同时触发时，**回合玩家优先，场上越早登场的越优先**；
   - 能力轮到结算时，如果来源已经离场就**失效**，谢幕曲例外；
   - 超进化的随从**在己方回合内**不受伤害、不会被能力破坏；
   - 一个效果让双方主战者同时归零时，**回合玩家判负**。
5. **已有开源项目。** 最完整的是 SWB-RL（MIT 协议）。
   - 规模：约 19 万行（含测试），用 JSON DSL 描述卡牌规则，数据快照截至第 8 弹。
   - 作者自述"尚未形成强战术"：PPO 联盟训练没有练出强 AI。这也说明**先做搜索，再做强化学习**的顺序更稳。
   - 我们**不直接 fork 它**：它核心的结算文件就有 1.8 万行，难读也难改，而且不包含第 9 弹。
   - 我们**把它当参照物**：拿同样的局面在两边各跑一遍，比对结果（差分测试）。详见 [card-pool.md §5](card-pool.md#5-已有开源项目)。

├──────────────────────────────────────────────────────────────┤
│ AI 层     RandomAgent · 贪心 · ISMCTS · PPO / 价值网络        │  agents/

├──────────────────────────────────────────────────────────────┤
│ 规则引擎  回合流程 · 交战 · 进化 · 触发队列 · 胜负判定        │  core/engine.py
│ 效果原语  伤害 · 回复 · 破坏 · 消失 · 召唤 · 抽牌 · 增益 …    │  core/effects.py

├──────────────────────────────────────────────────────────────┤

│                                                              │  core/script.py, cards/
├──────────────────────────────────────────────────────────────┤

**依赖方向只能自上而下。** `core/` 里不出现任何具体卡牌的代码：引擎只知道"入场曲""谢幕曲"这类钩子，不知道"波涛副船长"。

## 4. 核心数据模型

### 三条铁律
1. **所有可变状态都放在 `GameState` 里**，别的地方都不存状态。
2. **卡牌脚本无状态。** 卡牌需要记住的东西（比如某个计数）存在 `CardInstance.counters` 里。
3. **随机数只来自 `state.rng`。**

有了这三条：
- `clone()` 就等于把对局分支出一份，搜索算法可以随便试；
- 种子加动作序列就能完整复现一局，调试和复盘都方便；
- 对状态做"确定化"采样（§8）也很简单。

### 4.1 CardDef：印刷数据（不可变）

| 字段 | 含义 |
|---|---|
| `card_id` | 官方 8 位卡号（演示卡用 1–99） |
| `name, craft, type, cost, atk, life` | 卡名、职业、类型（随从 / 护符 / 吟唱护符 / 法术）、费用、攻击力、生命值 |
| `keywords` | 卡面上独立成行的关键词（守护、疾驰、突进、毁灭、虹吸、潜行、屏障、威慑、灵气） |
| `countdown` | 吟唱护符的吟唱值 |
| `traits` | 种族（海盗、骑士、创造物……） |
| `related` | 官方 `related_card_ids`：这张牌能产生的衍生物 |
| `faith, accelerate, crystallize` | 信仰、激奏、结晶形态（另一张 CardDef） |
| `name_zh, card_set, rotation, is_token, has_ability` | 官方中文名、卡包、是否指定系列可用、是否衍生物、有没有能力文字 |
| `text` | 卡面文字（只在本地加载官方数据时有），用于审核脚本 |

官方数据没有进化后身材这个字段，因为规则统一规定进化 +2/+2、超进化 +3/+3。

### 4.2 CardInstance：一张牌在对局中的实例（可变）

| 字段 | 含义 |
|---|---|
| `uid` | 对局内唯一编号。clone 之后不变，所以行动可以用它引用卡牌 |
| `cost, atk, life, max_life, keywords` | 当前值，会被各种效果修改 |
| `evolved, super_evolved` | 是否已进化 / 超进化 |
| `entered_turn, attacks_made, max_attacks` | 判断召唤失调和攻击次数 |
| `order` | 登场序号，用来实现"越早登场越先结算" |
| `countdown` | 当前吟唱值 |
| `fate` | 离场方式（在场 / 被破坏 / 消失），用于判断击退等效果 |
| `engaged_turn, fused_turn` | 本回合是否启动过 / 融合过 |
| `silenced, no_last_words` | 被去除所有能力 / 被去除谢幕曲 |
| `grants` | 效果赋予的能力、身材、关键词（可带到期回合） |
| `cost_mods` | 按顺序生效的费用修改 |
| `counters` | 卡牌脚本自己的状态 |

### 4.3 PlayerState / GameState
- **PlayerState**：主战者生命和上限、能量点（PP）、进化点（EP）、超进化点（SEP）、额外能量点、己方回合数、连击、协作计数、墓场数、本局被破坏的随从和护符（亡者召还等要用）、使用过的原本费用、入场记录、进化次数、主战者伤害上限和"受到的伤害 +N"，以及牌组 / 手牌 / 战场 / 主战者区域四个区域。战场按登场顺序排列，最早登场的在最前。
- **GameState**：双方玩家、随机数生成器、先手方、当前行动方、全局回合数、阶段（换牌 / 对战 / 结束）、胜者、uid 和登场序号计数器、触发队列。**每个行动结束时触发队列一定是空的**，所以 clone 不需要复制队列。

## 5. 行动模型

| 行动 | 含义 |
|---|---|
| `Mulligan(indices)` | 开局换牌：选择要换掉的手牌位置 |
| `PlayCard(uid, targets, modes)` | 使用手牌，目标和模式一并给出 |
| `Attack(attacker, target)` | 随从攻击：目标是随从 uid，或者敌方主战者（用负 uid 表示） |
| `Evolve(uid, super_, targets, modes)` | 用进化点或超进化点进化；"进化时：再发动一次入场曲"这类能力可以重新选目标和模式 |
| `Engage(uid, targets, modes)` | 启动场上的护符 |
| `Fuse(uid, cards)` | 把手牌里的若干张牌融合到一张带融合的牌上 |
| `UseBonusPP()` | 后手方按下额外能量点按钮 |
| `EndTurn()` | 结束回合 |

**关键设计：所有选择都"折叠"进行动里。** 打出一张"入场曲：选择一个敌方随从造成 3 点伤害"的牌，就是一个完整的 `PlayCard(uid, targets=(敌方随从,))`。引擎结算时不会中途停下来问玩家。

为什么不用别的方案：
- **协程或生成器**（结算到一半 `yield` 出去等输入）：Python 的生成器没法复制，搜索就做不了。
- **"暂停等待输入"的状态机**：每个效果都要能中断和恢复，复杂度翻倍。超凡世界的目标和模式几乎都在使用卡牌时就确定了，没必要付这个代价。
- **预留的口子**：真要遇到结算中途才能做的选择，再加一个 `state.pending` 字段和一个 `Choose` 行动，只给那几张牌用。

**动作空间的规模。** 合法行动由 `legal_actions()` 枚举，通常是几个到几十个。
- 手牌里完全相同的牌（卡号、费用、身材、关键词、计数都相同）只生成一组行动；选手牌当目标时也一样（例如弃 1 张金币和弃另一张金币算同一个选择）。
- 给神经网络用时，再把行动映射成"行动类型 → 来源位置 → 目标位置"三段式的固定编号加掩码（§9.3）。

## 6. 规则引擎

### 6.1 对局流程
1. **开局**：洗牌，双方各抽 4 张。后手方获得额外能量点。
2. **换牌**：先手、后手依次换牌：把选中的牌放到一边，重新抽同样数量，再把放到一边的牌洗回牌组。
3. **回合开始**（`_start_turn`），依次：
   1. 己方回合数 +1；
   2. PP 上限 +1（最多 10），PP 回满；
   3. 后手方第 6 回合刷新额外能量点；
   4. 重置本回合的进化标记、连击、随从攻击次数和"本回合攻击过主战者"标记；
   5. 先主战者区域、后战场，按登场顺序：吟唱值 -1（归零就破坏），并把"回合开始时"能力入队；手牌里"在手牌中也发动"的卡的回合开始能力也入队；
   6. 对手的"对手回合开始时"能力入队；
   7. 检查回合开始时的瞬念召唤；
   8. 结算队列；
   9. **最后抽 1 张牌**，再结算一次队列。
4. **主阶段**：玩家反复选择行动。
5. **回合结束**（`_end_turn`），依次：
   1. "回合结束时"能力入队（主战者区域、战场、手牌里会发动的卡），再入队对手的"对手回合结束时"能力；
   2. 排在它们后面的是"检查回合结束时的瞬念召唤"。所以瞬念召唤看到的是回合结束能力结算之后的场面，而这些能力引发的谢幕曲排在召唤之后（官方 Q&A：混沌监狱·阿兹弗特先被破坏，然后瞬念召唤断绝的轮回·泽勒尔，最后才结算阿兹弗特的谢幕曲）；
   3. 结算额外能量点：如果还剩至少 1 点 PP，这次使用作废，按钮恢复可用；
   4. 到期的"直到回合结束"效果失效：身材、关键词、赋予的能力、费用修改、主战者伤害上限；
   5. 交换行动方。
6. **安全上限**：全局回合数超过 `max_turns` 就判平局。这只是防止死循环，**不是已确认的游戏规则**。

### 6.2 触发系统
- **入队**：`effects.enqueue(state, hook, source, controller, ...)` 只负责把触发加进队列。
- **结算**：`engine.resolve_queue` 按先进先出依次执行，每执行完一个就做一次死亡检查。
- **失效**：每个触发记着来源当时所在的区域（战场 / 手牌 / 牌组）。轮到结算时来源已经不在那里，就跳过。谢幕曲、法术本身、"被舍弃时"能力例外。
- **监听**：`effects.emit` 把一个事件广播给所有会响应的卡，顺序是回合玩家优先，主战者区域、战场、手牌、牌组，越早登场越优先。手牌和牌组里只有声明了 `listen_in_hand` / `listen_in_deck` 的卡才会收到事件。
- **触发时判定的条件**：卡面写"回合结束时，如果本随从已进化"这类条件，默认在结算时检查。需要在**触发那一刻**检查的，脚本把钩子名写进 `queue_checks` 并实现 `queue_condition`，入队时不满足就不入队（官方 Q&A：被同一个回合结束里更早的能力（比如土之法则·伽莱翁）进化的克己复礼的修女·拉姆蕾达不发动；大游戏世界在卡牌使用时就判定）。
- **入场时**：`on_enter` 是"本卡进入战场时"能力，不论是使用、召唤、复制还是瞬念召唤进场都会触发，排在其他卡的"每当有随从进入战场"之前。每位玩家还有一份本局入场记录（`PlayerState.entered`，卡号 → 次数），用来回答"本局有几张某某进入过战场"。
- **使用卡牌时的入队顺序**：
  1. 这张牌自己的入场曲（法术则是法术效果）；
  2. 对"你使用了卡牌"做出反应的卡（`on_play`，比如海盗旗的"每当你使用法术"、信仰的"每当你使用爆能强化过的卡牌"）；
  3. 这张随从自己的"进入战场时"（`on_enter`）；
  4. 对"有随从进入战场"做出反应的卡（`on_ally_enter` / `on_enemy_enter`）。

  这些反应**在使用卡牌的那一刻就入队**，所以在这张牌结算过程中才出现的卡不会对它做出反应。例如黄金时代召唤的海盗旗，不会被这张黄金时代推进（已经由玩家确认）。
- **同时死亡**的随从，按回合玩家优先、登场越早越优先的顺序入队谢幕曲（`GameState.field_order()`）。
- **死亡检查**：每个效果原语执行完，都会把生命值 ≤ 0 的随从破坏掉，并把它们的谢幕曲排进队列。卡面上的一句话结算完之前，谢幕曲不会插进来执行。

### 6.3 交战
官方规则加社区整理的 9 步交战顺序，骨架实现了其中的主干：

1. 宣告攻击。攻击次数 +1，攻击方失去潜行。
2. 攻击方的"攻击时"和"交战时"能力入队并结算。
3. 防守方如果还在场，它的"交战时"能力入队并结算。
4. 如果第 2、3 步已经把防守方破坏掉，而攻击方是超进化的，触发击退（对敌方主战者造成 1 点伤害）。
5. 双方同时造成伤害，结算屏障、超进化无敌和虹吸。
6. 生命值 ≤ 0 的随从被破坏；带毁灭的随从破坏交战对象。毁灭算"被能力破坏"，所以会被超进化无敌挡住。破坏顺序是攻击方一侧在前。
7. 防守方被破坏、攻击方是超进化的，触发击退。击退在谢幕曲之前结算。
8. 结算队列（谢幕曲等）。

攻击主战者时：攻击方的"攻击时"和"攻击主战者时"能力先结算，然后是伤害和虹吸。

### 6.4 进化
- **解锁时机**：先手方从己方第 5 回合起可以进化、第 7 回合起可以超进化；后手方分别提前到第 4、第 6 回合。
- **次数**：每回合只能用点数进化一次，进化和超进化二选一。
- **数值**：进化 +2/+2，超进化 +3/+3，都按普通增益处理。进化后的随从在登场当回合就能攻击随从。
- **触发**：用点数进化时触发"进化时"能力；用超进化点时，先触发"进化时"，再触发"超进化时"。
- **效果引起的进化**（`effects.evolve`）：只改变数值和状态标记，不触发这两类能力，符合官方 Q&A。卡面写"本随从进化时"的能力（`on_evolved`）任何方式的进化都会触发。已经进化的随从不能再进化。
- **只在超进化时选目标**：卡面只有"超进化时：选择……"的牌用 `super_evolve_targets` / `super_evolve_modes`，普通进化时不会列出无用的目标选择。

### 6.5 胜负判定
- 主战者生命值降到 0 时，**立即**判负。后面的效果不再结算，触发队列被清空。
- 一个效果打到双方主战者时，按回合玩家优先的顺序结算（`effects.leaders_turn_order`）。这样"双方同时归零"时，自然是回合玩家先归零、判负。
- 需要从空牌组抽牌时判负；手牌已满（9 张）时抽到的牌直接销毁，墓场 +1。

### 6.6 实现进度
指定系列用到的机制已经全部实现：

- **基础**：PP、额外能量点、换牌、抽牌、爆牌、空牌组判负；九个静态关键词，无视守护，每回合攻击多次，不能攻击；
- **能力时机**：入场曲、谢幕曲、进化时、超进化时、本随从进化时、攻击时（随从 / 主战者）、交战时、被舍弃时、抽到时、本卡进入战场时、受到伤害时、获得增益时、回合开始 / 结束、对手回合开始 / 结束；
- **监听**：使用卡牌、随从入场（己方 / 敌方）、己方随从进化、攻击、卡牌被破坏、启动、土之秘术、抽牌、主战者回复；手牌和牌组里也能发动的卡；
- **职业机制**：爆能强化（含"改为全部发动"）、模式、协作、连击、觉醒、启动、融合、结晶、激奏、唤灵、亡者召还、土之印 / 土之秘术、魔力增幅、瞬念召唤、奥义 / 解放奥义、信仰；
- **区域移动**：召唤、复制（保留伤害和效果）、变身、返回手牌 / 牌组、从牌组召唤、消失、"离场时消失"；
- **修改**：限时或永久的身材、关键词、赋予的能力；按顺序生效的费用修改（加减、设为、减半）；去除所有能力；去除谢幕曲；主战者生命上限、伤害上限、"受到的伤害 +N"；
- **对局记录**：本局被破坏的随从和护符、使用过的原本费用、入场记录、进化次数、上回合是否攻击过主战者；
- **其他**：卡组合法性检查、官方卡组哈希编解码、同名手牌去重（身材、费用、计数器都相同才算同一张）。

**已知的近似处理**（代码里标了 `APPROX`）：

| 卡牌 | 近似之处 |
|---|---|
| 威胁的残渣 | 爆能强化后仍需要有可选目标才能使用 |
| 纹章：转动的《命运之轮》·斯洛士 | 吟唱归零时纹章先被破坏、回合开始能力不再发动，第三次发动改由谢幕曲完成 |

还没有做的：追踪已公开的手牌信息（§8）。
## 7. 卡牌脚本系统

### 7.1 CardScript 接口

```python
class CardScript:
    # 选择：折叠进使用这项能力的行动里
    play_targets / evolve_targets / super_evolve_targets / engage_targets   # TargetSpec 元组
    enhance: tuple[int, ...]                # 爆能强化费用：能付得起的最高档会被强制使用
    modes / evolve_modes / super_evolve_modes / engage_modes   # (选项数, 选几个)
    modes_all_when_enhanced: bool           # "爆能强化：改为全部发动"

    # 静态属性（被赋予的能力也算）
    attacks_per_turn, engage_cost, fuse_filter, skybound, listen_in_hand, listen_in_deck,
    invoke_at, unplayable, indestructible, damage_cap, cant_attack, banish_on_leave,
    ignores_ward, suppresses_fanfare, queue_checks

    # 自身钩子
    fanfare / cast / last_words / on_evolve / on_super_evolve / on_evolved / strike /
    follower_strike / leader_strike / clash / engage / on_turn_start / on_turn_end /
    on_opponent_turn_start / on_opponent_turn_end / on_discard / on_drawn / on_spellboost /
    on_fuse / on_invoked / on_buffed / on_damaged / on_enter
    # 监听钩子
    on_play / on_ally_enter / on_enemy_enter / on_ally_evolve / on_attack /
    on_card_destroyed / on_engage / on_earth_rite / on_draw / on_leader_healed
```

`Ctx` 里有：对局状态、卡牌实例、控制者，以及这次使用时做的选择（目标、模式、是否爆能强化）。`ctx.chosen()` 取仍在场上的目标，`ctx.chosen_hand()` 取仍在手牌里的目标。脚本通过 `effects` 模块里的原语改变对局：`damage`、`heal_leader`、`buff`、`destroy`、`banish`、`summon`、`draw`、`draw_matching`、`add_to_hand`、`discard`、`advance_countdown`、`add_to_leader_area`、`gain_max_pp`、`recover_pp`、`evolve`、`set_leader_max_hp`、`give_leader_damage_cap`、`random_sample`……

激奏形态在官方数据里是另一张卡（另一个卡号），所以它有自己的脚本；引擎根据当前 PP 自动决定用哪种形态（`engine.play_form`）。

### 7.2 示例：用真实卡牌写脚本
以海盗皇家牌组里的**波涛副船长**为例（完整实现见 `svsim/cards/sword.py`，有改动以代码为准）。卡面：入场曲：选择 1 个敌方随从造成 3 点伤害，召唤 1 个令人战栗的海盗旗。进化时：再发动一次入场曲。超进化时：把黄金短剑和黄金项链加入手牌，并把它们的费用变为 0。

```python
@register(ROUGHWATER_FIRST_MATE.card_id)
class RoughwaterFirstMate(CardScript):
    play_targets = (TargetSpec(Target.ENEMY_FOLLOWER),)
    evolve_targets = (TargetSpec(Target.ENEMY_FOLLOWER),)

    def fanfare(self, ctx):
        self._raid(ctx)

    def on_evolve(self, ctx):          # 用超进化点时也会触发这一句
        self._raid(ctx)

    def on_super_evolve(self, ctx):
        for token in (GILDED_BLADE, GILDED_NECKLACE):
            card = E.add_to_hand(ctx.state, ctx.controller, token)
            if card:
                card.cost = 0

    def _raid(self, ctx):
        E.damage(ctx.state, ctx.chosen(), 3, ctx.source)
        E.summon(ctx.state, ctx.controller, DREAD_PIRATES_FLAG)
```

### 7.3 为什么用 Python 脚本，不用 JSON DSL
SWB-RL 用 JSON 描述卡牌规则（`trigger` + `operations`），这样可以审计、可以批量生成，代价是需要先设计并维护一整套 DSL 解释器。

我们用 Python 脚本：
- 好读，可以直接打断点调试；
- 碰到特殊卡牌，不用回头扩展 DSL；
- 每张牌通常只有 5–15 行，全卡池约 586 个脚本、每个职业一个模块；
- 共性模式提炼成了辅助函数（`cards/common.py` 和各职业模块里的 `_summon`、`_buff_others` 等）。

全卡池是 8 个并行的 AI 工作者各写一个职业，再由人合并、统一改用引擎功能的。AI 写的卡牌逻辑会出错，所以每张卡都要求有测试，拿不准的规则标 `UNSURE` 留给人确认（§13）。

### 7.4 一张卡的实现流程
1. `python -m svsim.tools.fetch_cards` 拉取官方数据，加载器自动生成 CardDef。
2. 阅读卡面文字和这张卡的官方 Q&A。
3. 写脚本。可以让 AI 起草，**必须人工审核**：Jason 的经验和 SVsim 项目里的解析错误都说明，AI 写的卡牌逻辑会出错。
4. 每张卡至少写一个测试；官方 Q&A 一条转成一个测试。
5. **覆盖率检查**，两道：
   - 静态：`decks.unimplemented()` 列出有能力文字却没有脚本的牌（只有关键词的牌不需要脚本）。`tests/test_full_pool.py` 对整个卡池检查一遍，目前为空；
   - 运行时：`python -m svsim.tools.coverage --decks random` 用随机卡组跑对局，列出从没触发过的钩子。15000 局里 826 个钩子触发了 824 个，剩下两个（卓越创造物Ω 的入场曲、宏大的回归）要靠特定连锁才能生成，各有单元测试。

### 7.5 卡牌数据放在哪里
- **卡池数值表**：`svsim/cards/data/rotation.json`，由 `tools/build_pool.py` 从官方接口生成，提交在仓库里。每张卡只有对战用的字段：卡号、英文名和中文名、职业、类型、费用、身材、关键词、吟唱值、种族、卡包、稀有度、衍生物关系、纹章 / 信仰 / 激奏 / 结晶形态，以及"有没有能力"这一位。**不含卡面文字、Q&A 和卡图。** `cards/pool.py` 把它加载成 `POOL`，测试不依赖下载的数据。
- **能力**：每个职业一个模块（`neutral.py`、`forest.py`……`portal.py`），用 `card(卡号)` 取数值、用脚本写能力。脚本的文档字符串是给维护者看的效果摘要。
- **卡面文字和 Q&A**：用 `fetch_cards.py` 拉到本地 `data/raw/`（不提交）。`tools/card_text.py` 按职业列出卡面、Q&A 和脚本完成情况，写脚本时对照用。
- **防止过期**：`tests/test_card_data.py` 在本地有官方数据时，逐张核对数值表。平衡调整之后重新生成数值表并跑测试，被加强或削弱的卡会直接报出来。

## 8. 隐藏信息与随机性
- **`observe(state, player)`**：返回这位玩家能看到的信息：自己的手牌，双方战场、生命、PP、EP、SEP，对手的手牌数和牌组数。
- **`determinize(state, player, rng)`**：复制一份状态，把对手的手牌和牌组打乱后重新分配，把自己牌组的顺序也打乱，再重置随机种子，得到"一种可能的真实局面"。信息集蒙特卡洛树搜索（ISMCTS）每次迭代都在这样一个确定化的局面上搜索。
- **假设**：观察方知道对手的卡组构成，固定卡组训练时成立。以后可以改成"按卡组类型的分布采样"。
- **待实现**：追踪已公开的信息。例如从场上返回手牌的牌、被对手复制走的牌，确定化时不能把它们打乱。

## 9. AI 接口与路线

**对局要点**（来自实战经验）：海盗皇家 vs 跳费龙的关键，是皇家护卫用前期的动作压住龙族的出伤，一直撑到自己"牌效 × 费用"超过龙族，尤其要限制龙族的 999 大哥（焦灰的安纳提玛·班德奈特）入场。设计局面评估函数、挑选测试局面、检验 AI 打法时都以此为依据，比如看龙族 9 费之前的场面压力，以及双方累计的资源交换。

### 9.1 斩杀求解器（第一个实用工具）
- **搜索范围**：只在自己的回合内，对所有出牌、攻击、进化的顺序做深度优先搜索。
- **加速**：用局面哈希做置换表，相同局面只算一次；剪掉明显无意义的分支，比如攻击后什么也没击杀的路线（Cygames 在 CEDEC 2016 分享过同类思路）。
- **随机效果**：遇到随机效果时停止展开，或者采样多次求概率。
- **输出**：能不能斩杀、斩杀路线，或者"场面评估最高"的打法。

### 9.2 ISMCTS 陪练
- **搜索**：每次迭代先确定化，再在 clone 出来的副本上做蒙特卡洛树搜索；模拟阶段先用随机或简单启发式策略走到终局。
- **规则一致性**：对手 AI 和斩杀求解器用的是同一个引擎，所以它们的结论在规则上一致。

### 9.3 Gym 环境与强化学习（后期）
- **观测编码**：手牌 9 个位置、双方战场各 5 个位置、两个主战者，每个位置一个特征向量，包括 card_id 嵌入（封闭词表）、费用、攻击力、生命值、关键词位、进化状态；再加上 PP、EP、SEP、回合数等全局特征。
- **动作编码**：行动类型 → 来源位置 → 目标位置，每一段都配合法动作掩码。思路和 Jason 项目里的（卡槽, y, x）一样。
- **训练经验**，来自 Jason 的视频：
  - 先用最简单的网络；
  - 训练时盯着 `approx_kl`、`clip_fraction` 和熵；
  - 慎用奖励塑形；
  - 对手按"随机 → 规则型 → 历史版本自对弈"的顺序逐步加强。
- **更推荐的方向**：AlphaZero 式的"价值网络 + 搜索"。SWB-RL 的结果已经说明，纯 PPO 很难练出强战术。

## 10. 性能
测量环境是单核 Python，随机对局：

| 指标 | 海盗皇家 vs 跳费龙 | 随机卡组（全卡池） |
|---|---|---|
| 完整对局 | 约 170 局/秒（约 1.2 万次行动/秒） | 约 140 局/秒 |

- **热点**：合法行动生成（`_play_actions`、`play_form`、同名手牌去重）占一半以上时间，其次是触发的入队和广播。
- **优化顺序**：
  1. 缓存每回合不变的部分（比如手牌的使用形态），减少重复计算；
  2. 用手写的复制函数替代 `copy.copy`，牌组写时复制；
  3. 还不够快，就把核心用 Rust（PyO3）重写，Python 接口保持不变。
- **原则**：每次优化之前都先用 profiler 找热点。

## 13. 待确认的规则问题
1. 超凡世界是否有回合上限（初代是第 40 回合双方判负）。引擎现在用 `max_turns` 兜底。
2. 进化点、超进化点被回复后能否超过 2；能否在解锁回合之前使用。
3. 融合是"每回合 1 次"，还是"每张带融合的牌每回合 1 次"（英文和日文描述不一致）。
4. 0 点伤害能否击破非超进化随从的屏障。引擎现在按"任何一次受伤事件都会击破"处理（依据：超进化随从受到 0 点伤害时屏障也会消失的 Q&A，以及"0 点伤害也算受到伤害"）。
5. 随机效果能否选中潜行随从。推测可以，因为限制写的是"被选择"。
6. 奥义里的"当前回合数"指全局回合数还是己方回合数。
7. 法术进入墓场的时机，是结算前还是结算后。引擎现在放在结算后。

### 已确认的卡牌细节
2026-10-05 由玩家确认，测试里都有对应用例：
- 黄金时代召唤的海盗旗，**不会**被这张黄金时代本身推进（反应在使用卡牌时就入队，见 §6.2）。
- 伊德梅塔进化时信仰值不足 5：**什么都不发生**，不扣信仰值，也不获得能力。日文原文是"信仰値を-5して、…を持つ"，按惯例这是一个要先付得起的消耗。
- 两张伊德梅塔都进化，"+1/+1"能力**会叠加**，之后每张爆能强化的牌给 +2/+2。
- 触发信仰"+1/+1"的那张爆能强化随从，自己**也能**吃到 +1/+1。

2026-10-05 第二批（全卡池），同样都有用例或注释：
- 天司长的继承者·圣德芬被瞬念召唤后被对手的森林陷阱破坏：**仍然获得纹章**（"被瞬念召唤时"在本卡离场后照样结算，只是无法返回手牌）。
- 从本局被破坏的卡里随机挑选时，**被破坏次数越多越容易被选中**（混沌监狱·阿兹弗特，以及崇高的天书、崇高的憎恶·康蒂玛、器械操纵者·吉尔克等）。
- 万食的安纳提玛·拉拉安瑟姆进化时没有敌方随从可选，**仍然进行土之秘术**。
- 超进化随从受到 0 点伤害时屏障也会消失；引擎按"任何一次受伤事件都会击破屏障"实现。
- 以下按原先的实现确认：巴别隆城空手启动仍推迟吟唱值；进化的 +2/+2 算获得增益（露芙蕾、蒂亚）；慈惠的心腹包括自己的进化；丘比丹计量 ≥15 时奥义和解放奥义都发动；卡婕、卡特斯罗特纹章的"每回合一次"（前者没目标也算用掉，后者只在真正进化时算）；罗德诺艾尔四世两档爆能强化叠加；希耶提包括自己；骁勇骑士的"最左边"是最早登场的；琳库露纹章可以把生命上限降到 0；赛菲满场融合仍扣 2 PP；波摇花的裁决的 X 按被销毁的牌的费用算；伊斯坦戴德 对 玛尔奇盖特纹章照样破坏敌方随从；莉迪耶尔的自伤在模式之后；审理的守卫、天书深渊、艾尔拉德纹章按英文的条件理解；索菲娜沿用拉姆蕾达的 Q&A；回复 0 点也触发"回复时"；锻磨保镖没目标也回复；尤斯提斯没目标也进化。

  core/            规则引擎（不含任何具体卡牌）

    state.py       CardInstance / PlayerState / GameState

    effects.py     效果原语、死亡检查、职业机制
    engine.py      对局准备、合法行动、行动结算、回合流程、交战、进化
    view.py        observe / determinize
  cards/
    data/rotation.json  指定系列卡池数值表（不含卡面文字）
    pool.py        加载数值表：POOL、card(卡号)、collectible(职业)
    common.py      各职业共用的目标规格和小工具
    neutral.py forest.py sword.py rune.py dragon.py abyss.py haven.py portal.py
                   各职业的卡牌脚本（含衍生物、纹章、信仰、特殊形态）
    library.py     导入全部职业模块，注册所有脚本
    decks.py       卡表、卡组合法性检查、"有能力却没脚本"检查、随机合法卡组、哈希导入导出

    demo.py        18 张演示卡（不是真实卡牌，用来测试规则）
