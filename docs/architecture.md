# 超凡世界对战模拟器：架构设计

> 版本 v0.3（2026-10-05）· 全卡池完成：指定系列 516 张卡（含衍生物、纹章、信仰、特殊形态共 586 个有能力的卡牌定义）全部有脚本，任意两套合法卡组都能完整对战
> 配套文档：[规则摘要](rules-reference.md) · [卡池与数据源](card-pool.md)

## 0. 一句话目标

针对《影之诗：超凡世界》**指定系列（Rotation）**的几套固定卡组，做一个**规则准确、跑得快、可以复制和回放**的对战模拟器，在它上面依次搭建斩杀求解器、搜索型 AI，最后再接强化学习，用来当自己的陪练和复盘教练。

## 1. 目标与非目标

| 目标 | 说明 |
|---|---|
| 规则准确 | 以官方规则、官方词汇表和官方卡牌 Q&A 为准，每条规则都有测试 |
| 先做透再铺开 | 先做透 2 套卡组（M2），再铺开到指定系列全卡池（M2.5）；规则引擎本身是通用的 |
| 可复制、可回放 | `state.clone()` 能分支对局；种子加动作序列能完整复现一局 |
| 对 AI 友好 | 统一的 `legal_actions / apply / clone / observe / determinize` 接口 |
| 快 | 能支撑搜索和训练；早做性能分析（Jason 视频里的教训） |

**非目标**
- **不接入真实游戏客户端。** 用户协议禁止外部工具、机器人和逆向工程，详见 [card-pool.md §6](card-pool.md#6-法律与使用边界)。真实对局只用于人工复盘。
- **以指定系列为主。** 指定系列的牌全部实现，轮换后跟着卡池更新。无限模式只支持玩家指定的卡组（目前是破魔虫精灵），为这些卡组补写需要的牌；无禁止、起始系列不在范围内。
- **暂不做图形界面。** 先做命令行，以后再考虑网页。

## 2. 调研得出的设计约束

1. **卡池是封闭的。** 指定系列一共 515 张牌、56 个衍生物，没有任何"从全卡池随机生成"的效果，只有复制对手卡组或手牌里的牌（仍在两套卡组的范围内）。
   - 一局里可能出现的牌，就是"双方卡组 + 它们的衍生物"，词表是固定的。神经网络可以直接给每个 card_id 学一个嵌入向量，不需要理解卡面文字。
2. **官方数据只有数值是结构化的。** 官方 JSON 接口提供费用、身材、类型、职业、关联衍生物和 Q&A，**能力只有自然语言文本**。所以：
   - 数值和独立成行的关键词自动导入；
   - 能力逐张手写脚本。卡面文字里的 `<ev>`、`<sev>`、`<ridx>` 标记可以辅助切分。
3. **官方 Q&A 是现成的测试用例。** 数据库里有 120 张卡、共 165 条官方裁定，可以直接转成回归测试。
4. **规则本身决定了引擎骨架**（细节见规则摘要）：
   - 触发能力进入**先进先出队列**，结算中不会被打断，新触发排到队尾；
   - 同时触发时，**回合玩家优先，场上越早登场的越优先**；
   - 能力轮到结算时，如果来源已经离场就**失效**，谢幕曲例外；
   - 超进化的随从**在己方回合内**不受伤害、不会被能力破坏；
   - 一个效果让双方主战者同时归零时，**回合玩家判负**。
5. **已有开源项目。** 最完整的是 SWB-RL（MIT 协议）。
   - 规模：约 19 万行（含测试），用 JSON DSL 描述卡牌规则，数据快照截至第 8 弹。
   - 作者自述"尚未形成强战术"：PPO 联盟训练没有练出强 AI。这也说明**先做搜索，再做强化学习**的顺序更稳。
   - 我们**不直接 fork 它**：它核心的结算文件就有 1.8 万行，难读也难改，而且不包含第 9 弹。
   - 我们**把它当参照物**：拿同样的局面在两边各跑一遍，比对结果（差分测试）。详见 [card-pool.md §5](card-pool.md#5-已有开源项目)。

**依赖方向只能自上而下。** `core/` 里不出现任何具体卡牌的代码：引擎只知道"入场曲""谢幕曲"这类钩子，不知道"波涛副船长"。

## 4. 核心数据模型

### 三条铁律
1. **所有可变状态都放在 `GameState` 里**，别的地方都不存状态。
2. **卡牌脚本无状态。** 卡牌需要记住的东西（比如某个计数）存在 `CardInstance.counters` 里。
3. **随机数只来自 `state.rng`。**

有了这三条：
- `clone()` 就等于把对局分支出一份，搜索算法可以随便试；
- 种子加动作序列就能完整复现一局，调试和复盘都方便；
- 对状态做"确定化"采样（§8）也很简单。

### 4.1 CardDef：印刷数据（不可变）

| 字段 | 含义 |
|---|---|
| `card_id` | 官方 8 位卡号（演示卡用 1–99） |
| `name, craft, type, cost, atk, life` | 卡名、职业、类型（随从 / 护符 / 吟唱护符 / 法术）、费用、攻击力、生命值 |
| `keywords` | 卡面上独立成行的关键词（守护、疾驰、突进、毁灭、虹吸、潜行、屏障、威慑、灵气） |
| `countdown` | 吟唱护符的吟唱值 |
| `traits` | 种族（海盗、骑士、创造物……） |
| `related` | 官方 `related_card_ids`：这张牌能产生的衍生物 |
| `faith, accelerate, crystallize` | 信仰、激奏、结晶形态（另一张 CardDef） |
| `name_zh, card_set, rotation, is_token, has_ability` | 官方中文名、卡包、是否指定系列可用、是否衍生物、有没有能力文字 |
| `text` | 卡面文字（只在本地加载官方数据时有），用于审核脚本 |

官方数据没有进化后身材这个字段，因为规则统一规定进化 +2/+2、超进化 +3/+3。

### 4.2 CardInstance：一张牌在对局中的实例（可变）

| 字段 | 含义 |
|---|---|
| `uid` | 对局内唯一编号。clone 之后不变，所以行动可以用它引用卡牌 |
| `cost, atk, life, max_life, keywords` | 当前值，会被各种效果修改 |
| `evolved, super_evolved` | 是否已进化 / 超进化 |
| `entered_turn, attacks_made, max_attacks` | 判断召唤失调和攻击次数 |
| `order` | 登场序号，用来实现"越早登场越先结算" |
| `countdown` | 当前吟唱值 |
| `fate` | 离场方式（在场 / 被破坏 / 消失），用于判断击退等效果 |
| `engaged_turn, fused_turn` | 本回合是否启动过 / 融合过 |
| `silenced, no_last_words` | 被去除所有能力 / 被去除谢幕曲 |
| `grants` | 效果赋予的能力、身材、关键词（可带到期回合） |
| `cost_mods` | 按顺序生效的费用修改 |
| `counters` | 卡牌脚本自己的状态 |

### 4.3 PlayerState / GameState
- **PlayerState**：主战者生命和上限、能量点（PP）、进化点（EP）、超进化点（SEP）、额外能量点、己方回合数、连击、协作计数、墓场数、本局被破坏的随从和护符（亡者召还等要用）、使用过的原本费用、入场记录、进化次数、主战者伤害上限和"受到的伤害 +N"，以及牌组 / 手牌 / 战场 / 主战者区域四个区域。战场按登场顺序排列，最早登场的在最前。
- **GameState**：双方玩家、随机数生成器、先手方、当前行动方、全局回合数、阶段（换牌 / 对战 / 结束）、胜者、uid 和登场序号计数器、触发队列。**每个行动结束时触发队列一定是空的**，所以 clone 不需要复制队列。

## 5. 行动模型

| 行动 | 含义 |
|---|---|
| `Mulligan(indices)` | 开局换牌：选择要换掉的手牌位置 |
| `PlayCard(uid, targets, modes)` | 使用手牌，目标和模式一并给出 |
| `Attack(attacker, target)` | 随从攻击：目标是随从 uid，或者敌方主战者（用负 uid 表示） |
| `Evolve(uid, super_, targets, modes)` | 用进化点或超进化点进化；"进化时：再发动一次入场曲"这类能力可以重新选目标和模式 |
| `Engage(uid, targets, modes)` | 启动场上的护符 |
| `Fuse(uid, cards)` | 把手牌里的若干张牌融合到一张带融合的牌上 |
| `UseBonusPP()` | 后手方按下额外能量点按钮 |
| `EndTurn()` | 结束回合 |

**关键设计：所有选择都"折叠"进行动里。** 打出一张"入场曲：选择一个敌方随从造成 3 点伤害"的牌，就是一个完整的 `PlayCard(uid, targets=(敌方随从,))`。引擎结算时不会中途停下来问玩家。

为什么不用别的方案：
- **协程或生成器**（结算到一半 `yield` 出去等输入）：Python 的生成器没法复制，搜索就做不了。
- **"暂停等待输入"的状态机**：每个效果都要能中断和恢复，复杂度翻倍。超凡世界的目标和模式几乎都在使用卡牌时就确定了，没必要付这个代价。
- **预留的口子**：真要遇到结算中途才能做的选择，再加一个 `state.pending` 字段和一个 `Choose` 行动，只给那几张牌用。

**动作空间的规模。** 合法行动由 `legal_actions()` 枚举，通常是几个到几十个。
- 手牌里完全相同的牌（卡号、费用、身材、关键词、计数都相同）只生成一组行动；选手牌当目标时也一样（例如弃 1 张金币和弃另一张金币算同一个选择）。
- 给神经网络用时，再把行动映射成"行动类型 → 来源位置 → 目标位置"三段式的固定编号加掩码（§9.3）。

## 6. 规则引擎

### 6.1 对局流程
1. **开局**：洗牌，双方各抽 4 张。后手方获得额外能量点。
2. **换牌**：先手、后手依次换牌：把选中的牌放到一边，重新抽同样数量，再把放到一边的牌洗回牌组。
3. **回合开始**（`_start_turn`），依次：
   1. 己方回合数 +1；
   2. PP 上限 +1（最多 10），PP 回满；
   3. 后手方第 6 回合刷新额外能量点；
   4. 重置本回合的进化标记、连击、随从攻击次数和"本回合攻击过主战者"标记；
   5. 先主战者区域、后战场，按登场顺序：吟唱值 -1（归零就破坏），并把"回合开始时"能力入队；手牌里"在手牌中也发动"的卡的回合开始能力也入队；
   6. 对手的"对手回合开始时"能力入队；
   7. 检查回合开始时的瞬念召唤；
   8. 结算队列；
   9. **最后抽 1 张牌**，再结算一次队列。
4. **主阶段**：玩家反复选择行动。
5. **回合结束**（`_end_turn`），依次：
   1. "回合结束时"能力入队（主战者区域、战场、手牌里会发动的卡），再入队对手的"对手回合结束时"能力；
   2. 排在它们后面的是"检查回合结束时的瞬念召唤"。所以瞬念召唤看到的是回合结束能力结算之后的场面，而这些能力引发的谢幕曲排在召唤之后（官方 Q&A：混沌监狱·阿兹弗特先被破坏，然后瞬念召唤断绝的轮回·泽勒尔，最后才结算阿兹弗特的谢幕曲）；
   3. 结算额外能量点：如果还剩至少 1 点 PP，这次使用作废，按钮恢复可用；
   4. 到期的"直到回合结束"效果失效：身材、关键词、赋予的能力、费用修改、主战者伤害上限；
   5. 交换行动方。
6. **安全上限**：全局回合数超过 `max_turns` 就判平局。这只是防止死循环，**不是已确认的游戏规则**。

### 6.2 触发系统
- **入队**：`effects.enqueue(state, hook, source, controller, ...)` 只负责把触发加进队列。
- **结算**：`engine.resolve_queue` 按先进先出依次执行，每执行完一个就做一次死亡检查。
- **失效**：每个触发记着来源当时所在的区域（战场 / 手牌 / 牌组）。轮到结算时来源已经不在那里，就跳过。谢幕曲、法术本身、"被舍弃时"能力例外。
- **监听**：`effects.emit` 把一个事件广播给所有会响应的卡，顺序是回合玩家优先，主战者区域、战场、手牌、牌组，越早登场越优先。手牌和牌组里只有声明了 `listen_in_hand` / `listen_in_deck` 的卡才会收到事件。
- **触发时判定的条件**：卡面写"回合结束时，如果本随从已进化"这类条件，默认在结算时检查。需要在**触发那一刻**检查的，脚本把钩子名写进 `queue_checks` 并实现 `queue_condition`，入队时不满足就不入队（官方 Q&A：被同一个回合结束里更早的能力（比如土之法则·伽莱翁）进化的克己复礼的修女·拉姆蕾达不发动；大游戏世界在卡牌使用时就判定）。
- **入场时**：`on_enter` 是"本卡进入战场时"能力，不论是使用、召唤、复制还是瞬念召唤进场都会触发，排在其他卡的"每当有随从进入战场"之前。每位玩家还有一份本局入场记录（`PlayerState.entered`，卡号 → 次数），用来回答"本局有几张某某进入过战场"。
- **使用卡牌时的入队顺序**：
  1. 这张牌自己的入场曲（法术则是法术效果）；
  2. 对"你使用了卡牌"做出反应的卡（`on_play`，比如海盗旗的"每当你使用法术"、信仰的"每当你使用爆能强化过的卡牌"）；
  3. 这张随从自己的"进入战场时"（`on_enter`）；
  4. 对"有随从进入战场"做出反应的卡（`on_ally_enter` / `on_enemy_enter`）。

  这些反应**在使用卡牌的那一刻就入队**，所以在这张牌结算过程中才出现的卡不会对它做出反应。例如黄金时代召唤的海盗旗，不会被这张黄金时代推进（已经由玩家确认）。
- **同时死亡**的随从，按回合玩家优先、登场越早越优先的顺序入队谢幕曲（`GameState.field_order()`）。
- **死亡检查**：每个效果原语执行完，都会把生命值 ≤ 0 的随从破坏掉，并把它们的谢幕曲排进队列。卡面上的一句话结算完之前，谢幕曲不会插进来执行。

### 6.3 交战
官方规则加社区整理的 9 步交战顺序，骨架实现了其中的主干：

1. 宣告攻击。攻击次数 +1，攻击方失去潜行。
2. 攻击方的"攻击时"和"交战时"能力入队并结算。
3. 防守方如果还在场，它的"交战时"能力入队并结算。
4. 如果第 2、3 步已经把防守方破坏掉，而攻击方是超进化的，触发击退（对敌方主战者造成 1 点伤害）。
5. 双方同时造成伤害，结算屏障、超进化无敌和虹吸。
6. 生命值 ≤ 0 的随从被破坏；带毁灭的随从破坏交战对象。毁灭算"被能力破坏"，所以会被超进化无敌挡住。破坏顺序是攻击方一侧在前。
7. 防守方被破坏、攻击方是超进化的，触发击退。击退在谢幕曲之前结算。
8. 结算队列（谢幕曲等）。

攻击主战者时：攻击方的"攻击时"和"攻击主战者时"能力先结算，然后是伤害和虹吸。

### 6.4 进化
- **解锁时机**：先手方从己方第 5 回合起可以进化、第 7 回合起可以超进化；后手方分别提前到第 4、第 6 回合。
- **次数**：每回合只能用点数进化一次，进化和超进化二选一。
- **数值**：进化 +2/+2，超进化 +3/+3，都按普通增益处理。进化后的随从在登场当回合就能攻击随从。
- **触发**：用点数进化时触发"进化时"能力；用超进化点时，先触发"进化时"，再触发"超进化时"。
- **效果引起的进化**（`effects.evolve`）：只改变数值和状态标记，不触发这两类能力，符合官方 Q&A。卡面写"本随从进化时"的能力（`on_evolved`）任何方式的进化都会触发。已经进化的随从不能再进化。
- **只在超进化时选目标**：卡面只有"超进化时：选择……"的牌用 `super_evolve_targets` / `super_evolve_modes`，普通进化时不会列出无用的目标选择。

### 6.5 胜负判定
- 主战者生命值降到 0 时，**立即**判负。后面的效果不再结算，触发队列被清空。
- 一个效果打到双方主战者时，按回合玩家优先的顺序结算（`effects.leaders_turn_order`）。这样"双方同时归零"时，自然是回合玩家先归零、判负。
- 需要从空牌组抽牌时判负；手牌已满（9 张）时抽到的牌直接销毁，墓场 +1。

### 6.6 实现进度
指定系列用到的机制已经全部实现：

## 7. 卡牌脚本系统

### 7.1 CardScript 接口

```python
class CardScript:
    # 选择：折叠进使用这项能力的行动里
    play_targets / evolve_targets / super_evolve_targets / engage_targets   # TargetSpec 元组
    enhance: tuple[int, ...]                # 爆能强化费用：能付得起的最高档会被强制使用
    modes / evolve_modes / super_evolve_modes / engage_modes   # (选项数, 选几个)
    modes_all_when_enhanced: bool           # "爆能强化：改为全部发动"

    # 静态属性（被赋予的能力也算）
    attacks_per_turn, engage_cost, fuse_filter, skybound, listen_in_hand, listen_in_deck,
    invoke_at, unplayable, indestructible, damage_cap, cant_attack, banish_on_leave,
    ignores_ward, suppresses_fanfare, queue_checks

    # 自身钩子
    fanfare / cast / last_words / on_evolve / on_super_evolve / on_evolved / strike /
    follower_strike / leader_strike / clash / engage / on_turn_start / on_turn_end /
    on_opponent_turn_start / on_opponent_turn_end / on_discard / on_drawn / on_spellboost /
    on_fuse / on_invoked / on_buffed / on_damaged / on_enter
    # 监听钩子
    on_play / on_ally_enter / on_enemy_enter / on_ally_evolve / on_attack /
    on_card_destroyed / on_engage / on_earth_rite / on_draw / on_leader_healed
```

`Ctx` 里有：对局状态、卡牌实例、控制者，以及这次使用时做的选择（目标、模式、是否爆能强化）。`ctx.chosen()` 取仍在场上的目标，`ctx.chosen_hand()` 取仍在手牌里的目标。脚本通过 `effects` 模块里的原语改变对局：`damage`、`heal_leader`、`buff`、`destroy`、`banish`、`summon`、`draw`、`draw_matching`、`add_to_hand`、`discard`、`advance_countdown`、`add_to_leader_area`、`gain_max_pp`、`recover_pp`、`evolve`、`set_leader_max_hp`、`give_leader_damage_cap`、`random_sample`……

激奏形态在官方数据里是另一张卡（另一个卡号），所以它有自己的脚本；引擎根据当前 PP 自动决定用哪种形态（`engine.play_form`）。

### 7.2 示例：用真实卡牌写脚本
以海盗皇家牌组里的**波涛副船长**为例（完整实现见 `svsim/cards/sword.py`，有改动以代码为准）。卡面：入场曲：选择 1 个敌方随从造成 3 点伤害，召唤 1 个令人战栗的海盗旗。进化时：再发动一次入场曲。超进化时：把黄金短剑和黄金项链加入手牌，并把它们的费用变为 0。

```python
@register(ROUGHWATER_FIRST_MATE.card_id)
class RoughwaterFirstMate(CardScript):
    play_targets = (TargetSpec(Target.ENEMY_FOLLOWER),)
    evolve_targets = (TargetSpec(Target.ENEMY_FOLLOWER),)

    def fanfare(self, ctx):
        self._raid(ctx)

    def on_evolve(self, ctx):          # 用超进化点时也会触发这一句
        self._raid(ctx)

    def on_super_evolve(self, ctx):
        for token in (GILDED_BLADE, GILDED_NECKLACE):
            card = E.add_to_hand(ctx.state, ctx.controller, token)
            if card:
                card.cost = 0

    def _raid(self, ctx):
        E.damage(ctx.state, ctx.chosen(), 3, ctx.source)
        E.summon(ctx.state, ctx.controller, DREAD_PIRATES_FLAG)
```

### 7.3 为什么用 Python 脚本，不用 JSON DSL
SWB-RL 用 JSON 描述卡牌规则（`trigger` + `operations`），这样可以审计、可以批量生成，代价是需要先设计并维护一整套 DSL 解释器。

我们用 Python 脚本：
- 好读，可以直接打断点调试；
- 碰到特殊卡牌，不用回头扩展 DSL；
- 每张牌通常只有 5–15 行，全卡池约 586 个脚本、每个职业一个模块；
- 共性模式提炼成了辅助函数（`cards/common.py` 和各职业模块里的 `_summon`、`_buff_others` 等）。

全卡池是 8 个并行的 AI 工作者各写一个职业，再由人合并、统一改用引擎功能的。AI 写的卡牌逻辑会出错，所以每张卡都要求有测试，拿不准的规则标 `UNSURE` 留给人确认（§14）。

### 7.4 一张卡的实现流程
1. `python -m svsim.tools.fetch_cards` 拉取官方数据，加载器自动生成 CardDef。
2. 阅读卡面文字和这张卡的官方 Q&A。
3. 写脚本。可以让 AI 起草，**必须人工审核**：Jason 的经验和 SVsim 项目里的解析错误都说明，AI 写的卡牌逻辑会出错。
4. 每张卡至少写一个测试；官方 Q&A 一条转成一个测试。
5. **覆盖率检查**，两道：
   - 静态：`decks.unimplemented()` 列出有能力文字却没有脚本的牌（只有关键词的牌不需要脚本）。`tests/test_full_pool.py` 对整个卡池检查一遍，目前为空；
   - 运行时：`python -m svsim.tools.coverage --decks random` 用随机卡组跑对局，列出从没触发过的钩子。15000 局里 826 个钩子触发了 824 个，剩下两个（卓越创造物Ω 的入场曲、宏大的回归）要靠特定连锁才能生成，各有单元测试。

### 7.5 卡牌数据放在哪里
- **卡池数值表**：`svsim/cards/data/rotation.json`（指定系列和它们能产生的牌）和 `unlimited.json`（其余所有牌，`build_pool --format unlimited` 生成），由 `tools/build_pool.py` 从官方接口生成，提交在仓库里。每张卡只有对战用的字段：卡号、英文名和中文名、职业、类型、费用、身材、关键词、吟唱值、种族、卡包、稀有度、衍生物关系、纹章 / 信仰 / 激奏 / 结晶形态，以及"有没有能力"这一位。**不含卡面文字、Q&A 和卡图。** `cards/pool.py` 把它加载成 `POOL`，测试不依赖下载的数据。
- **能力**：每个职业一个模块（`neutral.py`、`forest.py`……`portal.py`），用 `card(卡号)` 取数值、用脚本写能力。脚本的文档字符串是给维护者看的效果摘要。无限模式卡组需要的非指定系列卡牌写在 `unlimited.py`，只写支持的卡组用到的牌。
- **无限模式卡组**：`decks.RHINO_FOREST`（破魔虫精灵，玩家提供的卡表）。核心是屠戮破魔虫（3 费 0/2，入场曲 +X/+0，X 为连击，疾驰）：先下便宜牌堆连击，再用昆虫的忠告、年幼宝石兽、圣树法杖把它弹回手牌反复下场打脸。为它补写了 9 张牌，引擎加了"己方随从离开战场"的监听（煌击战士·贝鲁要用）。`validate(deck, unlimited=True)` 按无限模式检查。
- **破魔虫精灵上的斩杀搜索**（120 个中后期局面：真实对局打到第 7–10 回合，手牌换成随机的连击手牌、至少一只破魔虫，对手血量随机 6–18；每个局面依次试 2000、2 万、10 万节点）：
  - 找到必杀 23 个，其中 2000 节点内 13 个、2 万节点内再多 5 个、10 万节点内再多 5 个；
  - **89 个局面搜到 10 万节点仍没有结论**（74%），每个局面中位数 68 秒；
  - 找到的必杀路线中位数 7 步、最长 13 步；
  - 23 个必杀里，按单张牌估的伤害有 16 个低于对手血量（筛选会跳过它们）。
  
  对照：海盗皇家 vs 跳费龙在 2000 节点下也只有 20% 的局面搜不完。连击卡组的出牌顺序太多，暴力搜索撑不住，需要按"资源流"理解卡组的斩杀规划（玩家的思路，见 §9.1）。
- **卡面文字和 Q&A**：用 `fetch_cards.py` 拉到本地 `data/raw/`（不提交）。`tools/card_text.py` 按职业列出卡面、Q&A 和脚本完成情况，写脚本时对照用。
- **防止过期**：`tests/test_card_data.py` 在本地有官方数据时，逐张核对数值表。平衡调整之后重新生成数值表并跑测试，被加强或削弱的卡会直接报出来。

## 8. 隐藏信息与随机性
- **`observe(state, player)`**：返回这位玩家能看到的信息：自己的手牌，双方战场、生命、PP、EP、SEP，对手的手牌数和牌组数。
- **`determinize(state, player, rng)`**：复制一份状态，把对手的手牌和牌组打乱后重新分配，把自己牌组的顺序也打乱，再重置随机种子，得到"一种可能的真实局面"。信息集蒙特卡洛树搜索（ISMCTS）每次迭代都在这样一个确定化的局面上搜索。
- **假设**：观察方知道对手的卡组构成，固定卡组训练时成立。以后可以改成"按卡组类型的分布采样"。
- **待实现**：追踪已公开的信息。例如从场上返回手牌的牌、被对手复制走的牌，确定化时不能把它们打乱。

## 9. AI 接口与路线

**对局要点**（来自实战经验）：海盗皇家 vs 跳费龙的关键，是皇家护卫用前期的动作压住龙族的出伤，一直撑到自己"牌效 × 费用"超过龙族，尤其要限制龙族的 999 大哥（焦灰的安纳提玛·班德奈特）入场。设计局面评估函数、挑选测试局面、检验 AI 打法时都以此为依据，比如看龙族 9 费之前的场面压力，以及双方累计的资源交换。

### 9.1 斩杀求解器（`search/lethal.py`，已实现）
- **搜索范围**：只在自己的回合内，对所有合法行动（出牌、攻击、进化、启动、融合、额外能量点、结束回合）的顺序做深度优先搜索，每一步在 clone 出来的副本上执行。局面的值是"本回合获胜的概率"。
- **不偷看**：模拟器知道牌组顺序和随机数，玩家不知道。一个行动如果用到了随机数，或者从牌组里拿了牌（`hidden_info` 在执行前后发生变化），就当作**机会节点**：不用模拟器自己的结果，而是换新的随机种子、重洗牌组，采样若干次取平均。只有不含机会节点的路线才算**必杀**（`sure`）；含运气的路线给出概率。对手的手牌按真实情况处理（自己回合里很少影响结果）。
- **结束回合**也是一个行动：回合结束能力打死对手、或者对手下回合要从空牌组抽牌，都算斩杀；对手回合里更晚发生的不算。
- **加速**：
  - 置换表：不同顺序走到的同一局面只算一次，键是除卡牌编号和随机数状态以外的全部状态（`state_key`）；
  - 行动排序：先试攻击主战者（攻击力高的先），再出牌、进化，最后才是攻击随从和结束回合；
  - 找到第一条必杀就停；节点预算用完就停，报告"没搜完"。
- **实测**（`tools/lethal.py bench`：海盗皇家 vs 跳费龙 30 局随机对局，每个回合开始的局面，预算 2000 节点）：
  - 595 个局面里，必杀 62 个（10%），只能靠运气的 6 个，没有斩杀 527 个；预算用完没搜完的 119 个；
  - 每个局面用时中位数 15 毫秒，95% 在 1.05 秒以内，最长 1.6 秒；
  - 同样的必杀局面，随机打法平均只打出 44%（每个局面试 20 次）；
  - 大搜索基本都在证明"没有斩杀"：75 个后期局面里，预算 2000 时搜不完的 24 个放到 40000 节点重搜，没有多找到必杀；在更大的 1181 个局面上，2000 节点比 2 万节点少找到 5 个必杀（122 个里的 4%）。
- **伤害估计筛选**（玩家提的思路，`screen` 参数）：大部分局面没有斩杀，而证明"杀不了"最花时间。先估这回合最多能打多少伤害：能打脸的攻击力，加上最好的一次进化，再加上 PP 限额内最好的一组手牌和启动（每张单独试打一次，量出直接伤害和新增的打脸攻击力）。估计够不着对方血量，就只做一次小预算搜索（默认 200 节点）。
  - 比赛卡组冒烟里探针找到、智能体没杀的 5 个回合（`analysis/smoke-missed-lethal/`，f824fad）：用智能体自己的斩杀判断（规划器 + 2000 节点、screen 200）重搜，5 个都搜不到。其中 3 个是这个筛选误判，只搜了 200 节点；不设筛选时 629～4991 节点就能找到。连击妖第 6 局第 13 回合、旗皇第 9 局第 21 回合、机锋第 30 局第 13 回合。另 2 个是 2000 节点不够（旗皇第 14 局、第 40 局，要 2170 / 3873 节点），作为已知限制先放着。
  - 处理（架构会话 2026-10-07）：筛选预算 200 → 1000，主预算不动。按"修正 + 不退化检查"做，不走胜率闸门：一是冒烟 400 局回放，3 个筛选误判要全部找回来；二是每回合用时增量 < 3%，满足就进 v2 的代码基线（和 v2r 一起合并）。arena 的 `+screen=N` 用来对比。
  - 结果：筛选预算全面改 1000，两项都没过。找回 3 个里的 2 个：机锋第 30 局要 4991 节点，比主预算 2000 还多，任何筛选值都找不回，归到"2000 节点不够"的已知限制（README 已改）。每回合用时平均 +81%～95%、90% 分位约翻倍：每次做决定都先查一遍斩杀，绝大多数局面都被筛，多给 800 节点就是给几乎所有局面加 800 节点。
  - 改成按差距给预算（`search.lethal` 的 `near`，arena `+screen=N:N2:K`）：被筛的局面里，估计离对手血量只差 K 点以内的给 N2 节点，其余仍是 N。冒烟里 1000 节点能找回的 8 个回合差距都是 1～4（连击妖第 6、30、34 局差 4、3、3，旗皇第 9、35、44 局差 2、1、1，ramp-t 第 40 局两边各差 3）。`200:1000:4` 的用时（四套各 50 局、同种子、机器只跑这一件）：平均 +7.8%、90% 分位 +9.8%、中位数 +0.5%，超过 3%。
  - 定（架构会话 2026-10-07）：仍然并进基线，`200:1000:4` 做默认（`agents.lethal_agent.NEAR`；`+screen=200` 是原来的做法）。理由：收益按冒烟 400 局估，1000 节点内能找回的漏杀回合 8 个（约 2% 的局），原来 5 个里有 3 个之后输了，约值 1～1.5 个百分点胜率；成本按规划器那次"1.6 倍算力只换 +2.2 点"折算，7.8% 的时间约值 0.3 点。预期值偏向开着，但两边都是粗估，600 局的门测不出这个量级，所以不跑门。以后所有候选的闸门两边都带这个默认，不引入偏差；陪练台每步多约 20 毫秒，可以接受。
  - 找回检查（337 个探针必杀回合）：screen 200 / 200:1000:4 / 1000 找到 317 / 325 / 325 个；1000 节点能找到的 8 个误判在 200:1000:4 下全部找回，没有 200 找得到、新默认反而找不到的（`analysis/smoke-missed-lethal/README.md`）。
  - **这是估计不是上界**（`damage_estimate` 的文档也写明）：每张牌单独试打，只在几张牌一起才成立的伤害会漏掉，例如连招（几张牌凑在一起才加攻）、连击数、先出的牌给后出的牌加伤害、一回合里攒起来的增益、融合 / 启动和其他牌的组合、额外攻击次数、打随从时触发的伤害。估计不到血量的局面只给小预算，组合斩杀就可能找不到。
  - 实测 1181 个局面，以 2 万节点搜索的结果为标准答案（122 个必杀）：

    | 做法 | 用时 | 漏掉的必杀 |
    |---|---|---|
    | 每个局面完整搜索（2000 节点） | 379 秒 | 5 个（预算不够） |
    | 估计不够就完全不搜 | 18 秒 | 19 个 |
    | 估计不够时只搜 200 节点 | 75 秒 | 7 个 |

    漏掉的多是连招：每张牌单独打几乎没伤害、凑在一起才致命（比如伊德梅塔的信仰 + 黄金时代爆能 + 超进化 1/1 疾驰），或者靠额外攻击次数。
  - 智能体默认用第三种：200 局对战从 629 秒降到 136 秒，胜率不变（72.5%）。练习题和分析用完整搜索。
- **资源流斩杀规划**（`search/combo.py`，玩家提出的思路）：连击卡组的出牌顺序太多，暴力搜索撑不住，而高手是"数资源"的。分三步：
  1. **自动画像**：在沙盒里（己方一个可弹回的随从、敌方两个 0/30 的随从）把每张牌在连击 1、3、5 下各试打一遍，量出净花费、回费、加入手牌的牌、抽牌数、能不能弹回己方场上的牌、直接打脸伤害、对敌方随从的伤害（指定一个、从最早的开始分摊、全体、随机）以及能不能穿过屏障，还有随从下场后的攻防、攻击力怎么随连击变化、本回合能打谁（疾驰能打脸，突进只能打随从）；启动、进化也一样量（天宫进化的分摊伤害量出来是"手牌数"）；手牌里的牌在己方随从离场时会不会减费（贝鲁）也量。比如破魔虫是"攻击 = 连击，疾驰"，磷光辉岩是"连击 3 以上多给一张 0 费的森林的奥秘"，驱逐的死矢是"随机 -0/-1 × 连击，能穿过屏障"，宝石兽超进化是"回 3 费"，都不是人写的；
  2. **抽象搜索**：在 PP、连击、手牌、己方随从（攻防、剩余攻击次数、能打谁、是否进化）、可启动的护符、进化点、额外能量点和敌方随从（攻防、守护、屏障）这些资源上搜最大伤害，遵守手牌上限 9 和战场上限 5：
     - **守护先拆**：有守护时什么都打不了脸。拆的办法：随从攻击（超进化的随从在自己回合不受伤害，撞死随从再击退 1 点；被反击打死的随从会离场，贝鲁随之减费）、指定伤害（贝鲁 4 点）、分摊伤害（魅禄模式 3、天宫进化）；**随机伤害只在敌方只有一个随从时才算**（昆虫的忠告、驱逐的死矢），否则当作没打中；屏障挡掉一次伤害；
     - **抽到的牌**占手牌格子但不会被打出（不知道是什么）；
     - **融合腾格子**（玩家的思路）：手牌快满时，可以把用不上的牌（比如天宫）融合进花园的指引，给妖精召集令的妖精、弹回的破魔虫腾出位置；融合过的指引打出来会抽 2 张；
  3. **引擎验证**：把最优方案翻译回真实行动执行一遍，打死对手才算斩杀；路线里有抽牌或随机效果的，还要在另外 16 种牌库顺序和随机结果下都打死才算。方案失败就退回精确搜索；抽象搜索的最大伤害够不着对手血量，就判定"模型认为杀不了"。
  
  实测（同样的 120 个破魔虫精灵局面）：

  | | 精确搜索（最多 10 万节点） | 第一版规划器 | 现在 |
  |---|---|---|---|
  | 找到的必杀 | 23 | 34 | **45** |
  | 判定杀不了 | 8（搜完） | 70 | 75 |
  | 没结论 | 89 | 16 | **0** |
  | 每个局面用时 | 中位数 68 秒 | 中位数 0.07 秒，最长 25 秒 | 中位数 0.06 秒，最长 7 秒 |

  第一版到现在多出的 11 个必杀，来自四处：验证不再因为"路线里抽了牌"就拒绝（改成在 16 种牌库顺序和随机结果下都要打死）；模型会拆守护；认识屏障；以及引擎对相同的手牌只列一张，规划器会换用同名的另一张。所有必杀路线都由规划器自己给出（中位数 8 步，最长 13 步），不再需要退回精确搜索。

  "模型认为杀不了"不是证明（模型没算场上卡牌的监听效果等），所以拿精确搜索复查了这 75 个局面：只找必杀、每个局面 15 万节点，**一个必杀都没找到**，其中 43 个搜完了全部可能（即证明杀不了）。已知答案的局面上模型也没出过错：23 个已知必杀全部找到，8 个已知杀不了的都判对。

  在另外 200 个新局面上（49 个对手有守护）：77 个必杀、117 个判定杀不了、6 个退回精确搜索仍没结论；每个局面中位数 0.07 秒，最长 24 秒。

- **玩家的速算公式**（`search/formula.py`）："先算打不打得死，再算怎么打"。k 只破魔虫的总伤害 = 每次下场时的连击数之和：打在所有破魔虫之前的牌每张值 k 点，夹在两次下场之间的回手牌只加给后面的（所以同样费用下"回手 2 虫"比"手出 2 虫"少 1 点）；0 费牌值 k；宝石兽超进化、魅禄进化回费相当于"-1 费的牌"；超进化撞死随从击退 1 点。牌的分类来自自动画像，不是卡表。
  - 第一轮和规划器对比（120 个局面，当时规划器还不会拆守护）：玩家原版公式在 34 个已验证的必杀里判对 27 个；补上对比中发现漏掉的两项后判对 32 个：**超进化最后一只破魔虫本身 +3（普通进化 +2）**，和**打出的辉岩再启动给破魔虫 +1**。在 70 个规划器判定杀不了的局面里，公式同意 67 个。
  - `combo.solve` 先算公式并附上分解说明，再由规划器给出实际路线。
  - **守护**：先算拆守护要多少资源、用什么拆。垫牌里的突进随从（妖精）顺手撞守护不花钱；贝鲁、魅禄的分摊模式是专门为拆守护打的；昆虫的忠告、驱逐的死矢的随机伤害只在守护是唯一的敌方随从时才算；进化天宫按手牌数算分摊伤害；场上随从可以改打守护（这部分就不打脸了）；也可以让第一只破魔虫去撞守护。屏障算多 1 点血。弹回破魔虫的那张牌来得太晚，不算拆守护：第一只破魔虫在它之前就要打脸。
  - **多出来的回手牌也是垫牌**：没用来弹破魔虫的昆虫的忠告可以把场上的妖精弹回来再打一次，等于两张牌两费（规划器先找到的打法）。
  - 现在的结果（加上守护、精确挑垫牌和进化的几种用法之后）：在这 120 个局面上和规划器完全一致（45 个必杀全判"打得死"，75 个杀不了全判"打不死"），但这是在同一批局面上边对比边改出来的。在另外 200 个没见过的新局面上：77 个必杀里判对 76 个，117 个杀不了里同意 109 个（另外 8 个公式偏乐观，"先粗算够不够"本来就该往这个方向错）。每次中位数 0.8 毫秒（精确挑垫牌比贪心慢一些）。
  - 对比中发现、补进公式的项：**垫牌按"最多张数"精确挑**（贪心会挑妖精召集令 + 两只妖精共 3 费 3 张，而召集令 + 一只妖精 + 辉岩 + 免费的森林的奥秘是 4 费 4 张）；**驱逐的死矢放在破魔虫之前最后打**，打几下就等于当时的连击数；**超进化的随从去撞守护**（宝石兽、魅禄回费的同时还能撞，撞死再击退 1 点；同一只妖精不能算两次）；进化回费的那张牌**必须真的打出来**；**先把场上打过的破魔虫弹回来**的回手牌排在所有下场之前，也值 k 点。
- **会斩杀的智能体**（`agents/lethal_agent.py`）：包一个别的智能体，每次决策前先搜斩杀，找到必杀就照着打完，否则交给被包的智能体。一次完整搜索没找到必杀之后，只有新回合或者出现了随机 / 抽牌才需要重搜（确定性的行动不可能凭空造出必杀）。随机智能体加上它，对纯随机智能体胜率 73%（200 局，开筛选后 72.5%）。
  - `planner=True`：资源流规划器排在精确搜索前面，验证过的路线直接照着打（对战工具里写成 `mcts:200+plan`、`greedy+plan`）。`trust_planner=True` 时，规划器判定杀不了的回合连精确搜索都省了。
  - 实测（`--decks rhino`：破魔虫精灵 vs 跳费龙，双方都是 ISMCTS 200 次模拟加斩杀搜索，400 局，每边操作破魔虫 200 局）：破魔虫一方不带规划器胜率 8%（15/200），带规划器 15%（30/200），每步思考时间 83 → 85 毫秒。规划器让胜率翻倍，但破魔虫仍然大幅落后：MCTS 的局面评估不懂连击卡组要"攒资源、憋一个斩杀回合"，前期就把破魔虫和回手牌打掉了，规划器只能在资源已经攒够时把斩杀找出来。下一步是让整盘的打法也看"下回合规划器能打多少"（斩杀威胁），见 §13。
- **斩杀练习题**（`tools/lethal.py puzzles`）：从对局里挑出"必杀、至少 3 步、不是全员打脸就能赢、随机打法 20 次里最多打出 5 次"的局面，用中文渲染局面和答案，存成可以复现的 JSON 行（卡组、种子、行动记录）。
- **以后**：这个求解器是后面学习型 AI 的"老师"和裁判：它给出的必杀路线可以当训练标签，也可以用来检验网络有没有漏斩杀。

### 9.2 完整对局 AI（已实现第一版）
**评估的约定（硬约束，玩家 2026-10-07）**：手牌的价值只能来自规划（这张牌在接下来一两回合的计划里贡献多少，推演后的分数差），或者来自与局面相关的特征（费用、回合数、手里其他牌的组合）。**不做按卡牌 id 的固定价值表**，训练时也不给单张牌学一个与局面无关的常数。玩家的原话："每张牌固定分数完全不可取——9 张妖精在 9 费后的价值完全小于龙族安娜题码 + 正义两张牌"。现装的线性模型因此只保留手牌张数，按功能分类的手牌特征（`me_hand_*` / `me_pool_*`）训练时清零（`learn/phased.py` 的 STOCK）。跨回合规划器里"留一张牌"的变体，要配上"下回合把它用掉"的计划再打分；潜力类特征要用，也只在推演后的局面上用。

- **局面评估**（`search/evaluate.py`）：给"轮到对手行动"的局面打分。双方各算一份再相减：
  - 主战者生命（越低每点越值钱）；
  - 随从的攻击、生命和关键词，护符、纹章；
  - 手牌数、没用的进化点 / 超进化点、PP 上限；
  - **危险**：对手场面下回合能不能打死我（大额扣分）；**压力**：我的场面能不能打死对手；
  - 牌组空了（下次抽牌就输）。
  
  权重是手设的初始值（`Weights`），之后用自对弈调，最终可以换成学出来的价值网络。
- **贪心智能体**（`agents/greedy_agent.py`）：每一步把所有合法行动各试一次，选评估最高的；没有比"现在结束回合"更好的就结束回合。带运气的行动用几次确定化采样打分，不偷看。起手换掉 5 费以上的牌。
- **ISMCTS**（`search/mcts.py`，单观察者信息集蒙特卡洛树搜索）：
  - 每次迭代先**确定化**：把对手的手牌和牌组、自己的牌组顺序、以后的随机结果重新打乱成一种可能的情况，所以 AI 不知道对手手里有什么；
  - 所有迭代共用一棵树，树上是自己这回合的行动序列。不同确定化里的同一个行动用"卡号 + 位置"对上（`action_key`），而不是卡牌编号；
  - 选择用带"可用次数"的 UCB：一个行动只在它合法的那些迭代里参与比较；
  - 新行动按"攻击主战者、出牌、进化、其他、攻击随从、结束回合"的顺序展开，然后用评估函数打分；结束回合时结算回合结束能力，但不进入对手回合；
  - 回传（默认）：一个行动的价值是它后面**最好的那条打法**，运气（确定化）取平均；不是它下面试过的所有打法的平均（见下面的"取最大值回传"）；
  - 最后走访问次数最多的行动。外面再包一层斩杀搜索（`full_game_agent`），有必杀就直接打。
- **竞技场**（`tools/arena.py`）：多进程循环赛，换座位、换卡组，报告胜率和每步思考时间。实测（每组 100 局，海盗皇家 vs 跳费龙）：

  | 对阵 | 胜率 | 每步用时 |
  |---|---|---|
  | ISMCTS(200) vs 贪心 | 73% ± 9% | 67 ms vs 30 ms |
  | ISMCTS(200) vs 贪心，7 职业随机卡组 | 73% ± 9% | 76 ms vs 33 ms |
  | ISMCTS(200) vs ISMCTS(1000) | 53% ± 10% | 67 ms vs 269 ms |
  | 贪心 vs 随机 + 斩杀（40 局） | 92% | |

  **模拟次数加到 5 倍没有提升**：现在只搜自己这一回合、用人工评估打分，搜得更多只是把粗糙的标准优化得更彻底。瓶颈是评估函数和对对手回合的预判，不是计算量。
- **人机对战**（`tools/play.py`）：终端里用中文和 AI 对战，可以随时让 AI 给建议（`h`）、查斩杀（`l`）。每局自动存到 `replays/`（卡组、种子、每一个行动；引擎在种子固定时是确定的，所以能原样回放），结束时打印一串回放码（zlib + base64，几百个字符），贴到聊天里就能交给别人复盘（`tools/records.py`）。
- **图形界面**（`web/index.html` + `ui/session.py`，玩家要求：命令行敲编号对操作量大的卡组太麻烦）：手机优先的单屏牌桌，对手在上、自己在下、手牌在拇指边。点手牌弹出它的所有打法（目标、模式、融合），点能攻击的随从会高亮可攻击的目标，直接点目标就攻击；AI 回合逐步播放；提示、查斩杀（先给速算）、备注、对局记录都在底栏。界面只负责画 `Session.view()` 给的数据、把玩家点的行动编号传回去，规则全在引擎里。两种运行方式共用同一个会话：
  - **本地服务器**（`tools/web.py`）：`python -m svsim.tools.web`，电脑浏览器打开，手机连同一个 Wi-Fi 也能打开；打完的局存到 `replays/`；
  - **浏览器内运行**（`tools/web.py --build`）：用 Pyodide（编译成 WebAssembly 的 Python）在网页的 Web Worker 里跑整个模拟器和 AI，不需要服务器，发布在 claude.ai 上手机直接打开。claude.ai 不提供压缩包文件，所以 svsim 和 Python 标准库的源码以 JSON 文本发布，Worker 把标准库在内存里组装成 Pyodide 要的 zip（Pyodide 取标准库的那次请求由 Worker 直接用内存数据应答：claude.ai 的安全策略不允许请求 blob: 地址，第一版因此在 Python 启动时退出），把 svsim 写进虚拟文件系统。每走一步都存两份：浏览器本地（手机把页面切到后台被回收、重新打开时自动恢复到中断前那一步）和页面自带的数据库（`games` 集合，Claude 可以直接读取复盘；换一台设备时开局页提供“继续上一局”）。恢复靠重放：引擎在种子和开局参数固定时是确定的。实测（桌面 Chromium）：3 秒就绪，AI（普通）一个回合约 1.2 秒。
- **对局记录的两个坑**（手机上打的头三局暴露出来的）：随机先后手会先从对局的随机数里取一个数，所以记录要存开局时的参数（`first_arg`），只存“谁先手”的话重放时洗牌全错（旧记录会自动识别）；重放模块要自己加载卡牌脚本，否则在新进程里重放时卡牌没有能力（磷光辉岩入场不给妖精）。测试里有“新开一个 Python 进程重放、逐项比对局面”的检查。
- **玩家对局分析**（2026-10-05，玩家用破魔虫精灵打 AI 的跳费龙，5 局全胜；AI 操作破魔虫打同样的对手只有 14～22%）：
  - 玩家的打法：中盘手牌几乎一直满（花园的指引 + 融合循环过牌、妖精召集令、发芽组员、大游戏世界），每回合 PP 花光但用在过牌和垫牌上，几乎不打脸；破魔虫和贝鲁留到斩杀回合，一回合出 6～10 张牌，破魔虫在连击 8～10 时下场，第 8～10 回合一波打死（斩杀前对手常常还是满血）。
  - 在玩家的 273 个决策点让 AI（`mcts:200+plan`）也选一次：只有 29% 一致。有分歧时 AI 最想打煌击战士·贝鲁（46 次，当 4 点解场随时用掉）、魅禄铺场、过早打出破魔虫；而 AI 自己的估值认为玩家的选择平均差 0.11 胜率。玩家 5 局全胜，所以是评估函数对这套牌错了，不是搜索不够深。
  - AI 操作的跳费龙前几回合常常空过，有能出的跳费牌也不出：手写权重里手牌 1.2 分一张、最大 PP 0.4 分一点，打出“最大 PP +1”的龙之启示在它看来是亏的。
  - 结论：手写的评估权重在不同卡组上错得不一样，下一步让权重（以及之后的价值网络）从对局里学出来。
- **学习评估函数**（`svsim/learn/`、`tools/learn.py`，玩家同意的两步同时做）：
  - 特征（`learn/features.py`）：双方各一组通用特征（血量、随从攻防和关键词、护符、手牌数、进化点、最大 PP、牌组、场面威胁、规划器算的“手牌下回合能打多少”和“满 10 费能打多少”），不针对任何卡组；模型是这些特征的逻辑回归（胜率），每套牌按职业各一份（`learn/weights/<职业>.json`），`+learned` 的智能体按自己卡组的职业取用，没有的退回手写评估。
  - 第 1 步，自对弈：每个回合结束时记下局面特征和这局最后谁赢，拟合胜率；再用学到的权重自对弈、重新拟合。
  - 第 2 步，玩家的对局：单步比较（玩家每一步应该比其他可选走法得分高）和整回合比较（玩家这一回合打完的局面应该比直接结束、AI 的打法、随机顺序打完的局面得分高），和第 1 步的目标合在一起优化。
  - 跳费龙：**成功**。对固定的破魔虫 AI 胜率 83% → 97%（各 100 局）；龙之启示第一次打出从中位数第 9 回合（100 局里只有 7 局打出过）提前到第 3 回合（58 局），前 4 回合 PP 利用率 69% → 83%。手写权重里最大 PP 太便宜，它自己学到了最大 PP 的价值。
  - 上线的是不带规划器特征的版本（`--no-potential`）：胜率同样 97%，每步 51 毫秒（不学习的 `mcts:100+plan` 33 毫秒，带规划器特征的版本更慢）。网页的三档强度都是 `+learned`，所以手机上的跳费龙 AI 已经会跳费。
  - 破魔虫：**还没成功**。对玩家思路的理解提高了：在没见过的对局上，整回合比较里把玩家那一回合排第一的比例，手写评估 23%，自对弈 + 玩家对局 50%，只用玩家对局 55%（随机 10%）；单步命中 29% → 30～35%。但交给 MCTS 实战反而更差（对固定跳费龙，各 200 局：原来 14%，学过的 2～5%，只用玩家对局学的 2%；加规划器提方案 8～16%，原来最好 22%）。原因：破魔虫 AI 自对弈几乎打不出正确的赢法，学到的是“弱 AI 的什么局面会输”（比如场上随从多就好），MCTS 照着它铺场；只用玩家的 5 局也不行：线性评估 + 一回合内的搜索表达不了“连续几回合攒资源、最后一回合爆发”，搜索会去钻模型的空子。下一步需要更多高手对局（现在对手变强了，玩家的对局重新有意义）和能表达手牌组合价值的非线性模型（价值网络）。
- **先打脸后进化**（玩家在对局备注里发现）：学习版跳费龙的「断头的斩姬·相枛津」（疾驰）两次先打脸 5 点、再进化/超进化，白白少打 2～3 点。在那两个局面上各重走 20 次：学习版 MCTS 次次先打后进化，手写评估的 MCTS 次次先进化再打，贪心（只看一步）两种评估都先打。
  - 原因不在“权重喜欢先打”：回合结束时两种评估都认为先进化再打更好（学习版 42.55 对 41.73）。问题是学习版的分数在 40 左右，换算成胜率 99.3%（它是对着弱的破魔虫 AI 学的，偏置项就有 +2.6），这时多打 2 点在胜率上只差 0.05%，搜索分不出来。
  - 修正 1（`search/moves.py`，和评估无关）：随从用完攻击次数后，如果它的进化只加身材（卡上没有进化效果，己方也没有对进化起反应的牌），就不再考虑进化它，因为先进化再攻击一定不差。MCTS 和贪心都用。
  - 修正 2（`ISMCTS`）：把“局面分数 → 0～1”的换算以搜索开始时的局面为中心，比较的是每条打法让局面变好还是变坏多少，评估自以为稳赢或稳输时也分得出好坏。单独用修正 2（不跳过）也能在那两个局面上 10 次全对。
  - 修正 3（`features.MONOTONE`，`fit(signs=...)`）：学习出来的系数里，“自己血量 ≤5”是正的、“对手血量 ≤5”是负的（等于乐意自己残血、不想把对手打残，来自训练对手的混杂因素）。训练时保持方向：自己血越多越好、对手血越少越好、场上必杀越多越好、牌组打空越差。已上线的跳费龙模型里这两个方向错的系数改为 0。
  - 实测（各 100 局，同一批种子）：学习版跳费龙新搜索对旧搜索（镜像）66% ± 9%；手写评估跳费龙新对旧 47% ± 10%（没有副作用）；破魔虫对同一个旧跳费龙，新搜索 17%、旧搜索 16%（没有退步）；跳费龙模型改系数前后对打 49%，改后对破魔虫 AI 97%。
- **整回合规划**（`search/turnplan.py`，竞技场里叫 `turn:N`，实验性，默认不用；玩家提醒：回合拉长以后，对这回合有利的动作可能对赢下整局不利）：自己的决定取最大值；抽牌、随机效果在发生那一刻重新洗牌、换随机数，按胜率取平均（不会预知抽到什么，也不会只按最好的运气打）；回合结束才打分；没碰到随机就照计划走完，碰到就重新规划。跳费龙的回合大多很便宜（预算 3000 个节点时平均 0.3 秒），破魔虫很贵（平均 1.5 秒，多数回合搜不完）。
  - 实测（各 100 局，对手是现在的 MCTS:200）：学习版跳费龙镜像 47% ± 10%，手写跳费龙镜像 55% ± 10%，破魔虫对手写跳费龙 20% ± 8%（同种子下用 MCTS 是 14%）。都在误差附近，没有明显提升。
  - 行为上正好是玩家担心的"这回合赚、整局亏"：用规划器的破魔虫，第 4～10 回合结束时平均只剩 4.8 张手牌、场上 2.2 个随从；MCTS 是 5.7 张、2.0 个；玩家（6 局）是 6.8 张、1.8 个。规划器把评估偏爱的铺场做到了极致，离高手"攒牌、斩杀回合一波打完"的打法更远了。结论：更强的回合内搜索放大的是评估函数的长远判断，瓶颈在评估（"回合结束时的局面值多少"），不在搜索的精确度。隔壁会话后来用同一个规划器（`turn:3000+plan+learned`）对现在的 `mcts:200+plan+learned` 跑了 200 局同种子的学习版镜像：58% ± 7%（再加"以起点居中"是 59%），和"纯取最大值"的 MCTS（60%）一致；这里的 47% ± 10% 只有 100 局，差距在两倍误差以内，更像抽样波动，不是方法的问题。
- **取最大值回传**（`ISMCTS(backup="max")`，现在是默认；玩家决定不做对比实验直接上线）：自己的回合里没有对手，一步棋的价值应该是它后面能接上的最好打法；原来按平均回传，"先进化再打""先打便宜牌攒连击""退回手牌再打一次"这类要接对后续才赚的走法，会被后面试过的差打法拖低，看起来不如直接结束回合。
  - 做法：每个节点记下每次确定化里它能走哪些行动（隐藏的牌和随机结果会改变能走什么），节点的估值 = 对这些"可走集合"按出现次数加权平均，每个集合取其中子节点的当前最好估值；没往下搜过的节点用它叶子评估的平均。每次回传沿路径重算，所以估值始终等于"现在这棵树上的最优打法"，不会因为早期的差模拟一直偏低。运气只取平均，不取最大（不预知抽牌）。`backup="mean"` 保留原来的平均回传。
  - 速度不变（每步 90 毫秒，平均回传 94 毫秒）；测试检查进化子节点的估值正好等于"进化 → 攻击 → 结束回合"那条线的值，平均回传则偏低。
  - 隔壁会话测的效果（各 100 局左右，纯取最大值，和这里的精确版思路相同）：学习版跳费龙镜像 60%，手写跳费龙镜像 56%，破魔虫对跳费龙 24%（平均回传 12%）。
- **Claude 亲自操作破魔虫**（玩家的提议，看会推理的玩家能打多少）：只看人类能看到的信息，不用提示和查斩杀，对网页"强"档的学习版跳费龙打了 5 局：1 胜 4 负（20%；后 3 局在明显输定时认输）。胜的一局是第 17 回合，靠连击 5 的破魔虫打出正好 5 点斩杀。输的原因：两次忘了"每回合只能进化一次"，计划好的宝石兽超进化回费落空；用零碎伤害去打，被三张诺玛格达拉（每张超进化回 6 血、留 8/9 守护）和伊兰翠回血全部回回去；为了解守护赔掉破魔虫，后期没有斩杀手段。对照：玩家用同一套牌 6 战全胜。也就是说，没有这套牌经验的通用推理，水平大约和现在的破魔虫 AI 一样（它对跳费龙 14%～20%）。高手多出来的是这套牌特有的判断：不去零碎打脸，攒满手牌，在 PP 和燃料足够的那一回合一次打满 20 点；破魔虫绝不拿去换守护。
- **胜负影响：双方时钟 + 对手回应**（`search/race.py`、`search/impact.py`、`tools/impact.py`，玩家的优先级：判断一个动作对"赢下这局"的影响比调搜索更重要）。玩家的几个要点：同一个动作在不同对局里影响完全不同，不能按固定汇率折算（过牌值多少，看能不能抽到伤害和能把费用用满的牌，代价是可能少打伤害、给对手多一个回合）；这两套牌几乎没有随从交互，**轮次就是货币**；换成有交互的卡组，轮次只是一个重要维度（解不掉的大怪踢一脚，不比直伤差）。所以不再给"手牌、场面"定固定分值，而是在每个局面上往前看，数"回合"：
  - **时钟**（`race.clock`）：一方还要再过几个自己的回合才能斩杀，假设对手不再处理。用引擎把这一方的回合往后推（PP 增长、按牌组顺序抽牌、倒数推进、回合开始效果结算，对手的回合什么都不发生；先确定化，不偷看牌组顺序）；每回合的爆发伤害取玩家的速算公式和规划器里大的那个；两种走法：攒着到第 k 回合一次打完（场上已有的随从在之前的回合每回合打一次），或者这回合按规划器打最多的伤害（在引擎里真的打出来）、下回合用剩下的和抽到的补完（"先打 15 再补 5"）。
  - **影响**（`impact.assess`）：同一回合的几种打法（你的、AI 的、直接结束），对同一批确定化（对手手牌和双方牌组重新抽样，各打法共用，差别来自打法而不是运气）各让对手的 AI 打一个回合，然后在你下回合开始时量：本回合（打脸、出牌、过牌、剩余 PP、手牌）、对手回应（是否被斩杀、还击多少、你的场面被解掉多少"能不能解"、对手花了多少 PP"要花多少"、对手场攻）、下回合能否斩杀、双方时钟、"时钟领先"（我方时钟先到的比例，我先动所以一样快算我先）、以及现在评估函数给的胜率（对照用）。
  - **在玩家 6 局上的检验**（每个玩家回合比较"你的打法"和 `mcts:200+plan` 从同一回合开始的打法，对手回应抽样 6 次；41 个回合两者打法不同）：现在的评估函数在 28 个回合里认为 AI 的打法更好，只有 12 个认为玩家的更好；"时钟领先"认为玩家更好的 19 个、AI 更好的 8 个（14 个持平）；"我方时钟"玩家更快 23 个、AI 更快 5 个。也就是说，高手的回合选择评估函数看不懂，用回合数来量就基本看得懂。典型的一回合：评估函数给玩家打法的胜率只有 1%，而那样打下回合 100% 能斩杀（玩家也确实下回合斩杀了）。
  - 其他发现：玩家比 AI 赢在**自己的时钟更快**，而不是拖慢对手（"对方时钟"玩家更好 18 个、AI 更好 15 个，差不多）；同一回合结束时 AI 留的手牌反而更多（AI 多 18 次、玩家多 7 次），打脸也更多（11 对 6）。所以"高手攒手牌"这个说法不准确：高手用掉的牌在为斩杀回合铺路（护符、PP、能循环的牌），手牌张数本身不是关键。
  - 时钟的已知局限：对手的处理、守护、回血都不算（所以叫"假设不处理"，对手的处理由抽样的那一个回合体现）；被大守护挡住时，不会"先花一回合解掉守护再爆发"（玩家第 6 局第 11、13 回合，时钟显示"5 回合内打不死"，实际第 17 回合斩杀）；投影时手牌满了就按规则爆牌，不会像玩家那样边循环边攒；规划器的路线有时在引擎里走不通（年幼宝石兽入场必须选一张己方的牌回手，场上只有护符时规划器以为可以不选，后面要启动的圣树法杖就被弹回手里了），这时只用走得通的前半段。
  - 拿来下棋（`impact:N`，`agents/impact_agent.py`）：每回合开始时（以及抽牌后原路线走不通时），在 MCTS 自己的打法、它次优的两个第一步各自接着打完、直接结束这几条路线里，按"时钟领先 + 0.25 × 估值 − 被斩杀"选一条照着打。破魔虫对手写跳费龙（`mcts:200+plan`），同一批种子各 100 局：31% ± 9%，对照 `mcts:200+plan` 27% ± 9%；成对看，10 局只有它赢、6 局只有对照赢，差别不显著；40% 的回合换了路线；每步约 1 秒（对照 0.1 秒）。也就是说**理解变好了，下棋还没有明显变强**：候选路线都来自原来的 MCTS（同一个评估函数），里面没有高手那种为斩杀回合铺路的打法，裁判再好也只能在给的选项里挑。下一步要让搜索提出这类候选（比如让规划器按"缩短我方时钟"生成路线），或者把时钟直接放进搜索的叶子估值（得先把时钟算快）。
  - **跳费**（玩家对跳费龙的说明，限这个对局：留牌围着跳费走，很多时候全换找跳费；金龙的激奏远比本体强；"3 跳 5、5 跳 7"，后面的伤害回合才能连续，比打低费牌更能领先伤害轮次）。时钟的"发育"回合因此会打跳费：哪些牌是跳费不靠卡表，而是在引擎里打一遍、看最大 PP 有没有涨（`race.ramps`：龙之启示、佐伊、金龙的激奏）；走法变成"先发育 j 个回合、再每回合打伤害"，对每个 j 取最快的。起手（先手 40 手随机）：手里没有跳费的期望时钟 5.85 回合，一张 5.44，两张 5.36。
  - **破魔虫的留牌**（玩家的规则，`agents/mulligan.py` 的 `PLAYER_RULES`）：5 费以上只有天宫和贝鲁。天宫一张牌能过牌、清场、给战场一次进化，对中速卡组甚至必留；贝鲁要减到 0 费才强，多数时候留一张更好（0 费贝鲁中盘返场、斩杀回合给虫加伤害都好用），超进化回合之后不太想抽到它，所以第二张换掉。很多低费牌反而不能留：年幼宝石兽要到超进化回合以后才有用，磷光辉岩、1 费的驱逐的死矢、枝叶大姐大也一样，看着便宜，要到中盘才厉害。换牌按"玩家给了规则的牌组 → 跳费牌组 → 换 5 费以上"的顺序取第一个适用的。破魔虫 AI 对学习版跳费龙，新旧留牌各 200 局都是 8%（成对 6 比 6）：现在的破魔虫 AI 后面打得太差，起手好坏体现不出来；这条规则主要等以后破魔虫 AI 变强、或者给玩家的起手做提示时用。
  - **换牌**按玩家的说法改了：一副牌里八分之一以上是跳费时，留跳费、其余全换（手里没有就全换）；别的牌组照旧换掉 5 费以上。对固定的破魔虫 AI 各 100 局，新旧换牌 91% 对 92%（这个对手太弱，看不出差别），第 5 个自己回合的最大 PP 5.70 → 5.97。也试过"按时钟挑换哪几张"：每种换法抽 6 次就要几秒，差别又在抽样误差以内（还会把金龙换掉），没有采用。
  - 回看玩家 10 局里 bot 的跳费：旧版（手写评估）手里有能打的跳费也几回合不打，最大 PP 只按自然增长；学习版有两局正好是"3 费龙之启示、5 费佐伊、7 费下大哥"，没做到的是金龙激奏（16 + 4 次能激奏只用了 1 次）和起手不找跳费（有一局到 7 费才摸到跳费）。在这些回合用时钟比较"bot 的打法"和"先激奏金龙"，3～4 费时激奏常常一样或更好，5 费以上能直接下 5、7 费大哥时 bot 的打法更好。
  - **解场先解谁**（玩家在第 10 局第 6 回合发现：跳费龙两把天刀面对萨莎妮德、妖精、发芽组员三个 1/1，解掉的是萨莎妮德和妖精，留下了发芽组员；而发芽组员会被年幼宝石兽弹回手里再下一次、连击 3 时再抽一张，是三个里最值钱的）。原因：评估只看随从的身材和关键词，三个 1/1 几乎一样，萨莎妮德多一个虹吸所以先解，妖精和发芽组员完全相同、随便选了一个。改法（`evaluate.latent_cards`、`hand_count`）：一方的牌组里有"把己方的牌弹回手"的牌时，它场上那些入场能抽牌、加牌的随从和护符，按"弹回再下一次能拿到几张牌"算进手牌数（在沙盒里按连击 3 量出来：发芽组员 1 张、磷光辉岩 2 张、妖精 0 张），手写评估和学习版评估都用这个手牌数。改后在那个局面重走 6 次，6 次都解掉萨莎妮德和发芽组员、留下妖精；对固定破魔虫 AI 100 局仍是 91%（没有副作用）。
  - 网页：复盘里新增"胜负影响"按钮，在你回合里的任意一步，比较"这回合剩下的部分"你的打法、AI 的打法（`mcts:100+plan+learned`）、直接结束，给出表格、每行含义和几句差别最大的结论；算一次存进对局记录（`record["impact"]`，按动作序号），下次直接显示。玩家已有的 6 局，每个回合的第一步已经预先算好（对手回应抽样 6 次）。
- **从玩家的对局学出牌时间**（`learn/timing.py`、`tools/timing.py`；玩家的方向：让 AI 自己学"什么时候用哪张牌、怎么规划轮次、为了赢该做什么"，而不是我一张张写规则）。玩家说的留牌规则，背后其实是时间：一张牌在第几个自己回合才派上用场，以及到那时自然抽到它的机会有多大。
  - **怎么数**：在玩家用某套牌打某个对手的对局里，逐张牌、逐个自己回合，数"这张牌有几张在手里"和"打出了几张"，得到每回合打出的机会（`hazard`），以及起手时每张牌留了还是换了（同名的第一张和后面几张分开数）。玩家 10 局破魔虫对跳费龙：发芽组员、妖精召集令、大游戏世界的打出回合中位数是 4～5，前 4 回合打出的机会 85%～100%；昆虫的忠告、磷光辉岩、驱逐的死矢中位数 7，破魔虫、年幼宝石兽、贝鲁中位数 8。
  - **留牌**（`agents/mulligan.py` 的第 0 层，优先于手写规则）：每张牌"留下的把握" = 先验 + 玩家自己的记录。先验是玩家说过的话（说要换就是 10%，说要留就是 90%，贝鲁第二张 10%）；没说过的牌看"留着它前 4 回合能打出去的机会"是否高于"换一张随机牌"的机会。再按玩家实际的留/换次数更新（先验算 2 局的分量）。结果和玩家说的规则完全一致，还多学到两条玩家没说、但每次都这样做的：昆虫的忠告 6 次全换，破魔虫本身也换。
  - **对局中**（`Timed`，竞技场里加 `+timing`）：评估里加一项"持牌价值"：手里每张牌按"玩家到这个回合还拿着它的机会"（`hold`）加分。第 4 回合拿着贝鲁值 0.82，拿着发芽组员只值 0.02，所以过早打出贝鲁、破魔虫、宝石兽会丢分，按时打出发芽组员几乎不丢。
  - **检验（留一局：用另外 9 局学时间，在剩下那局上看）**：一步一步地看，玩家的走法排第一的比例从 30% 到 36%（权重 8）；整回合看（玩家这回合打完的局面，对比直接结束、AI 的打法、3 种随机打法），玩家的打法排第一从 25% 到 55%（权重 8）、64%（权重 12）。（之前学线性评估，在没见过的对局上最好也是 55% 左右，但当时对比的打法不完全一样，不能直接比。）
  - **但下棋没有变强**（破魔虫 AI `mcts:200+plan` 对学习版跳费龙，同一批种子各 200 局）：对照 8%；加持牌价值，权重 3、8、12 分别是 6%、6%、4%（成对 8:12、10:13、7:14）。诊断（各 60 局）：加了持牌价值以后，第 4～9 回合平均手牌从 6.1 涨到 7.9（玩家 6.8），对局拖长 1.6 个回合，但单回合最大伤害还是 3.8，结束时跳费龙还有 15 血左右：**学会了攒，没学会什么时候把攒的牌打出去**。
  - **补上"什么时候兑现"**（`LethalAgent(burst=True)`，竞技场里加 `+burst`）：不能斩杀的回合，如果规划器"这回合打最多伤害"的路线打完以后，按时钟下回合就能斩杀，而攒着不打下回合斩杀不了，就照这条路线打（玩家的"先打 15 再补 5"）。结果：只加爆发 10%（成对 7:3）、单回合最大伤害 5.2 → 7.0；持牌 8 + 爆发 6%，持牌 3 + 爆发 8%，最大伤害 7.5～8.3。都在误差范围内。
  - **结论**：从对局学到的"什么时候用"让 AI 看起来更像高手（整回合排第一 25% → 55%～64%），留牌也学对了，但单独模仿时间不会赢。高手的打法是几块拼在一起的：攒牌、在对的回合一次打满 20 点、中间顶住跳费龙的伤害（解掉相枛津这类威胁、留血量余地）。AI 现在学到了第一块，第二块（爆发）只学到一半，第三块还没有。所以持牌价值和爆发先作为选项（`+timing`、`+burst`），不默认打开；留牌用学到的结果（和玩家说的一致，没有坏处）。
- **一晚上的尝试：破魔虫 AI 对跳费龙能不能到 50%**（玩家的要求；对手是网页"强"档的学习版跳费龙 `mcts:200+plan+learned`，各组合同一批种子 200 局，破魔虫一方都是 `mcts:200+plan` 加选项）。**没有做到**：所有组合都在 5%～13% 之间；最好的一组（保留 + 爆发 + 准备度）换一批种子各 400 局复核，对照 6%、它 8%，成对 20:16，不显著。
  - **诊断**（和玩家 10 局逐回合对比）：玩家猜对了一部分：AI 的破魔虫 56 次里 22 次拿去撞随从、22 次在第 6 回合前打出，玩家 25 次全部打脸、22 次在第 6 回合以后。但更大的差距在**过牌**：到自己第 8 回合，玩家平均已经抽过 25 张牌（牌组剩 15），AI 只抽过 17 张（剩 22～23）；玩家手里平均有 1.4 只虫，AI 只有 0.3～0.4 只；所以玩家的"下回合能打多少"（速算）第 8 回合是 14、第 9 回合 17，AI 一直是 2～4。玩家过牌主要靠花园的指引（每次 2 张）、发芽组员（22 次打出抽了 23 张，几乎每次都等到连击 3）、天宫、枝叶大姐大。
  - **试过的办法**（`+reserve` 保留破魔虫、`+burst` / `+burst2` 按时钟爆发 / 先模拟对手一回合再爆发、`+ready` 爆发准备度、`+timing` 持牌价值、`+pace` 按玩家节奏不提前出牌、`+patient` 连击牌等连击、`Weights.dig` 过牌加分、`+dig` / `+dig2` 规划器排"抽牌最多"的出牌顺序、降低场面权重、搜索加到 400 次、起手留破魔虫）：

    | 组合 | 胜率 | 单回合最大伤害 | 结束时龙的血量 |
    |---|---|---|---|
    | 对照（只有 `mcts:200+plan`） | 8% / 复核 6% | 5.2 | 15 |
    | 保留 | 6% | 4.4 | 15.3 |
    | 保留 + 爆发 | 12% | 7.4 | 10.9 |
    | 保留 + 爆发 + 准备度 0.25 | 13% / 复核 8% | 7.8 | 10.7 |
    | 保留 + 先模拟对手再爆发 + 准备度 | 12% | 5.3 | 13.9 |
    | 保留 + 爆发 + 持牌 3 | 7% | 7.9 | 11.0 |
    | 保留 + 爆发 + 按节奏 | 5% | 7.3 | 12.0 |
    | 保留 + 爆发 + 不拼场（随从权重降到 0.3/0.2） | 6% | 7.5 | 11.9 |
    | 保留 + 爆发 + 过牌加分 0.5 / 1 | 10% / 8% | 7.6 | 10.7 |
    | 保留 + 爆发 + 连击牌等连击（发芽组员抽牌率 28/55 → 48/51） | 8% | 7.9 | 10.5 |
    | 再加过牌顺序 / 大胆过牌 | 10% / 9% | 8.1 | 9.8 |
    | 全部加上（稳爆发） / 全部加上 + 搜索 400 | 6% / 7% | 4.4 / 8.1 | 15.5 / 9.8 |

    每一招都确实改变了它想改的那一项（破魔虫不再撞随从、发芽组员几乎每次抽牌、单回合最大伤害从 5 涨到 8、过牌多了 1～2 张），但胜率不动。
  - **结论**：玩家的打法是好几项同时做对（几乎每回合都把过牌打满、虫一直攒在手里、算准在哪个回合一次打满 20、中间只解必须解的威胁），单独补任何一项都换不来胜利；一回合深的搜索加手写评估，也不会自己把这些拼起来。要再往上走，可能需要一个"跨回合的规划器"（以几回合后打满 20 点为目标，倒推每回合该过牌、该留什么），或者用大量高手水平的对局去学策略。这些选项都保留为可选，不默认打开。（另外修掉了一个规划器漏洞：场上只有护符时年幼宝石兽必须弹回护符。）
- **跨回合规划器**（`agents/turns_agent.py`，竞技场里叫 `turns:N`；玩家认为值得做）：每回合开始时，把"这回合打哪一种"分成四种——斩杀/打最多伤害（KILL）、过牌（DIG：规划器排出抽牌最多、不打破魔虫和贝鲁的顺序，同时算上给贝鲁减了几费）、正常发育（DEV）、什么都不出（PASS，攒到下回合一起打）——每种都在几个确定化的局面里往后推演（之后的自己回合按"能斩杀就斩杀，否则过牌"，对手回合由贪心 AI 来打），按"杀死 1、被杀 0、否则看下回合能打多少、已经打了多少、自己还剩多少血"打分，选最好的一种。
  - 结果（各 200 局，对学习版跳费龙）：第一版 11%，加 PASS 10%，过牌同时追求贝鲁减费 8%。仍在同一个区间里。
  - 逐回合对比玩家又发现了几件事（这些是规划器还缺的"词汇"）：玩家前两回合常常什么都不出，第 4 回合一口气打两张死矢、两张发芽组员（第二张就能抽牌），第 6、7 回合用大游戏世界、昆虫的忠告把发芽组员、魅禄弹回来重下，一回合过 4～6 张牌；**贝鲁一直留在手里慢慢减费**：玩家第 8 回合 9 局里 8 局手里有贝鲁、平均 2 费、4 局是 0 费，AI 只有 11/26 局手里还有贝鲁、平均 5 费（早早拿去解场或下场了）；玩家第 8 回合还有 6.7 张手牌，AI 只剩 3.2 张；AI 第 2～3 回合几乎不过牌（每回合 0.2 张，玩家 0.9～1.7 张），把牌铺到场上、每回合打脸 2～3 点。
  - 也试了评估里少看自己的场面（0.3 倍）、手牌加价（2～2.5 分一张）：6%～8%。
- **打木桩：一套牌自己最快几回合能赢**（`search/race.py` 的时钟从换牌后起算；`learn/survival.py`、`tools/survival.py`）：让一套牌自己打，对手不出牌、不回血，看第几回合能打满 20 点。只用来回答"这套牌怎么赢、多快能赢"，不用来出牌。
  - 时钟多了一条过牌路线（`clock(..., digging=True)`）：每回合先走规划器排出的抽牌最多的顺序，留着破魔虫这类终结牌和贝鲁。没有写破魔虫专属的规则，它自己找到了"先过牌几回合、再一回合打出伤害"：不让它过牌，10 个自己的回合内只有约一半能打死对面。
  - 玩家的前提（直伤卡组）：不能指望随从滚雪球，应当假设随从都会被对手解掉；但不同随从站场蹭血的机会不同（1、2 费的妖精 1/1 往往能蹭到血，中期一定会被解掉）。所以时钟可以加上对手的解场（`removal`）：对手每个回合，己方每个随从按"同样血量的随从在这个对局里活过对手这一回合的比例"抽签决定去留（每个随从每回合抽一次，比较不同打法时抽到的结果一样）。这个比例从对局记录里数（`python -m svsim.tools.survival <对局> --play 80`，`--play` 让 AI 自己再打几局，不需要玩家的对局）；没有数据的对局按全部被解掉算。
  - 谁来解场很重要（玩家指出"实际对战中龙的大随从活不下来"）：学"对手会解掉多少"时，只用解场一方由玩家操作的对局，没有才用 AI 的对局。逐只追踪龙回合结束时场上 5 血以上的随从：玩家的 10 局里 24 只只有 1 只活到龙的下回合，玩家主要用虫风花·魅禄（7 次）、年幼宝石兽（5 次）攻击解掉，其余是天宫进化、驱逐的死矢、昆虫的忠告、妖精；AI 的破魔虫 80 局里 237 只活下 113 只（龙第 8～9 回合 70 只活下 56 只），宝石兽只解了 3 次，贝鲁却拿去撞了 17 次。第一版把两种对局混在一起学，龙的大随从后期存活率被算成 28%～83%。
  - 学到的存活率：破魔虫的 1 血随从活过龙第 1～5 回合的有 35%～48%，第 6～9 回合 0%～26%；3 血随从第 2～4 回合活下来 52%～85%，龙前期解不掉（龙一方由 AI 操作，用玩家 10 局 + AI 80 局）。跳费龙的随从活过破魔虫第 2～3 回合的有 18%～90%，第 5 回合以后 0%～19%（玩家的 10 局）。

    | | 随从不被解 | 全部被解 | 按学到的存活率 |
    |---|---|---|---|
    | 破魔虫精灵 | 195/200，第 6 回合 | 40/200，第 9.5 回合 | 94/200，第 9 回合 |
    | 跳费龙 | 200/200，第 6 回合 | 139/200，第 9 回合 | 170/200，第 8 回合 |

    随从不被解时，破魔虫第 6 回合就能打死，靠的是场面滚雪球，不现实。加上解场以后，时钟推到第 9 回合，接近玩家实战第 8～10 回合的斩杀。但时钟里只有一半的局能在 10 回合内打死，玩家几乎每局都能，说明规划器过牌和爆发还不如玩家（之前量过：玩家每回合过约 4 张，AI 约 2 张）。
- **进化点分配和资源规划**（玩家指出"AI 没理解进化点分配和资源规划的逻辑"；逐回合对比玩家的 10 局和 AI 破魔虫对学习版跳费龙的 80 局，AI 赢 7 局）：
  - 规则：进化点、超进化点各 2 个，先手自己第 5 / 7 回合解锁，后手第 4 / 6 回合；超进化 +3/+3，在自己的回合里不受伤害，撞死随从再击退对方主战者 1 点。破魔虫里和进化有关的牌：年幼宝石兽超进化回 3 费（入场弹回己方一张牌），虫风花·魅禄进化三选一（2 张妖精 / 回 2 费 / 3 点分摊伤害），天宫进化按手牌数分摊伤害。
  - 玩家的进化点（15 次）：魅禄 9 次（回 2 费 5、分摊 4），天宫 4 次（进化那回合开始时手牌平均 8 张，分摊 8 点清场）。超进化点（18 次）：宝石兽 9 次、魅禄 6 次；18 次里 14 次回费、14 次解场（11 次同时做到）——超进化的随从自己回合不受伤，撞死龙刚下的大随从，一个点换来"费用 + 解掉大随从 + 1 点伤害"。第二个超进化点常常留到斩杀回合：赢的 9 局里 5 局在斩杀回合超进化宝石兽回 3 费，多 3 费就是多 3 张牌、连击 +3、每只破魔虫 +3 攻。对局结束时平均只剩 0.5 个进化点、0.2 个超进化点。
  - AI 的进化点（158 次）：天宫 48、妖精 39、魅禄 19、贝鲁 19……；超进化点（142 次）：贝鲁 30、魅禄 29、妖精 27、天宫 21，宝石兽只有 12。300 次里 108 次（36%）没换到任何东西（不回费、不解场、不打脸，只是 +2/+2 站场），带回费的只有 17 次（玩家 33 次里 19 次）。魅禄的模式：玩家 15 次里 10 次回 2 费，AI 48 次里只有 5 次（多选妖精和分摊）。天宫进化时 AI 手牌平均 6.2 张。
  - 资源（第 6～9 回合的平均）：玩家手牌一直 8～9 张（上限 9），每回合回 1.1～1.8 费、出 4.7～6.8 张牌，PP 用光，斩杀回合以前几乎不打脸；AI 手牌 6～7 张，回 0～0.6 费、出 3.2～4.9 张，第 8～10 回合还剩 1～2 费没用，前期每回合零碎打脸 0.5～1.3 点（会被龙奶回去）。第 3～7 回合玩家每回合抽 1.2～2.1 张，AI 0.2～1.2 张。
  - 为什么：评估函数给没用的进化点固定 1 分、超进化点 1.5 分（`Weights.ep`、`sep`），和它们能换到什么无关；进化一只妖精让场面多 +2/+2，看起来就划算。AI 不知道"超进化点 = 3 费 = 斩杀回合每只虫 +3 攻"，也不知道"超进化的随从在自己回合撞大随从不掉血"；回费的好处要在同一回合把多出来的费用用掉才看得见，一回合一两百次模拟常常看不到。手牌数也一样：天宫进化的伤害、斩杀回合的连击都靠手牌，评估只按张数给固定分。
- **影子价格**（`search/prices.py`，竞技场里 `+survive`、`+points`、`+priced`）：按用途定价两样东西——己方随从按"活过对手这一回合的机会"打折（learn.survival）；没用掉的进化点按"留着它下回合能多打几点"定价（规划器有它、没有它各算一次；下回合只能进化一次，所以剩两个点时花掉一个不亏，剩最后一个时它值斩杀回合多打的伤害）。
  - 结果（各 200 局，`mcts:100+plan+reserve` 对学习版跳费龙）：原版 6%，`+survive` 2%，`+points` 6%，`+priced` 4%。
  - `+survive` 让"什么都没换到的进化"从 32% 降到 13%，手牌多 1～1.5 张；但 AI 不再铺场打脸（每回合 1.2 点降到 0.2～0.5 点），而零碎打脸正是它仅有的赢路（AI 赢的局第 7 回合龙只剩 8.4 血，输的局 18.4）。"攒燃料、一回合爆发"它还不会，旧的赢路又被拿掉，所以更差。
  - `+points` 几乎不起作用：AI 手里很少同时有虫和足够的牌，"留着超进化点下回合多打几点"多半是 0；宝石兽超进化 29 次变 33 次。
- **不借助玩家理解的对局分析**（玩家让我只从规则、卡表和模拟出发自己分析）：
  1. 伤害公式：一回合出 n 张牌、k 只虫放在最后，伤害 = k·n − k(k−1)/2；20 点要 2 只虫出 11 张，或 3 只虫出 8 张，龙有一个 6 血守护再多 2～3 张（同一只虫可以被宝石兽、昆虫的忠告弹回来再打）。每回合自然抽 1 张的话，第 8 回合只看过 12～13 张，手里有 2 只虫的概率 21%～24%；玩家第 8 回合看过 25 张，69%。所以前中期必须过牌。
  2. 玩家的 9 个斩杀回合：开始时龙 11～19 血（多是两回合打完）；先出 1～4 张 0 费牌（减到 0 费的贝鲁、磷光辉岩给的森林的奥秘），6 局超进化宝石兽回 3 费，打 2～3 次虫、连击 4～10。
  3. 跳费龙的时钟是大随从：解不掉的伤害（相枛津疾驰、璐米欧儿全场 4 点）一局约 7 点；大随从攻击对玩家只打了约 1 点，对 AI 约 10 点，AI 多在龙自己第 8～10 回合被打死。大随从落地当回合解掉，龙就没有斩杀能力。
  4. 第 7 回合开始时：手里的虫玩家 1.1 只、AI 0.9 只，差不多；差在斩杀回合的燃料：看过的牌 21 对 14～15、手牌 8.8 对 6～7、贝鲁最低费用 4.3 对 7.5～7.9、0 费牌 0.7 对 0～0.1。
  5. 没成的两个角度：用打木桩量每样资源值几个回合，100 局噪声太大（改动会打乱后面的抽牌），只看得出多 1 点 PP 约提前 0.4 回合、少了进化点或超进化点各慢约 0.3 回合；"10 费时手牌一回合最多打多少"当燃料指标，第 7 回合玩家 8.4、AI 8.0，分不开。
- **卡组分析器和环境卡组**（`tools/analyze.py`，报告见 [docs/meta-report.md](meta-report.md)；玩家让我去网上找 meta 卡组，和 AI 一起分析运转逻辑）：从 Game8 的 Tier 表（2026-10-06）用官方卡组码导入，能完整导入的是海盗皇家、跳费龙、连击精灵（T1）和快攻龙（T2）（`decks.COMBO_FOREST`、`decks.FACE_DRAGON`；网页也能选）。分析器不需要任何卡组知识：打木桩（随从不被解 / 全被解）、两两 AI 互打，再从记录里量胜率、赢的回合、伤害来源、回血、进化、打出来胜率最高的牌、随从存活。
  - "随从全被解"的打木桩把卡组分成两类：跳费龙 39/60、海盗皇家 20/60（海盗旗是护符）能在 10 回合内打死，快攻龙 6/60、连击精灵 1/60 几乎不能。

  - **玩家的评价：这份环境分析几乎没有价值**——AI 还没理解卡组怎么运转，建立在 AI 对局上的数字量的是 AI 怎么打，不是卡组怎么赢（跳费龙在 AI 手里 26%，人类环境里是 T1）。由此推出的"哪种卡组吃操作"收回。工具留着：等 AI 能把一套牌打对，或者拿高手的对局来量时再用。

- **用玩家的对局校准"尺子"，再按尺子挑打法**（`agents/fuel_agent.py`，竞技场 `fuel:N`、`+hpW`；玩家选"继续破魔虫"，目标是 AI 到 2000 CR 左右，练习才有价值）：
  - 尺子：玩家 10 局的 65 个回合，玩家的打法和 AI（`mcts:100+plan+reserve`）从同一开局的打法，让对手回应后打分。评估函数判玩家更好 13 次、AI 更好 47 次（AI 一直在照着一把和高手相反的尺子优化）；双方时钟按整回合计，多数分不出；"燃料"（对手回应后再过牌两回合，一回合最多能打多少）39 对 16；燃料 + 回应后血量的一半 41 对 15。
  - 按尺子每回合挑打法（候选：AI 原来的打法、先过牌再正常打、规划器的爆发线、什么都不出）：各 200 局对学习版跳费龙，原版 6%，燃料 3%，燃料 + 0.5×血量 2.5%，燃料 + 2×血量 4.5%。燃料版手牌多了（第 7 回合 7.7 张，原版 6.6）、贝鲁便宜了（6.5 费，原版 7.4），但第 7 回合血量只剩 10.4（原版和玩家都是 15.3）：它攒牌不解威胁，龙每回合打它 2.6～5.5 点。
  - 原因：尺子只量了自己的赢点。龙回合结束时场上有 5 血以上大随从的下一回合，AI 手里有超进化解场手段（超进化点 + 宝石兽或魅禄）时 93% 会解掉，但它只有 19% 的时候还留着这个手段（玩家 58%）。缺的是"把解场手段留到对手的威胁到来时"，也就是围绕对手的赢点规划资源。
  - 另外：从玩家同样的开局出发，规划器的过牌线每回合抽得不比玩家少（第 4 回合 2.0 张对 1.2 张，第 7 回合 2.4 对 1.9）；AI 看过的牌少，是整局走向的问题，不是单回合不会过牌。
- **玩家的跳费龙内战**（玩家用跳费龙打跳费龙 bot 10 局，10 胜，每局 2～3 分钟；和 bot 自己的 60 局内战对照）：
  - 一样的地方：换牌（留跳费牌、其余全换）和跳费速度（第 5 回合玩家 6.9 PP、bot 6.6，第 7 回合都是 9.2）。跳费本身不是差距。
  - 不一样的地方：玩家超进化班德奈特 6/10 局（第 6～8 回合），给对手焦灰徽记（每回合开始 2 点、每回合第一次回血再 1 点）；进化正义 7/10 局（第 6～10 回合，每回合结束 8 点）；伤害主要来自回合交替时的效果（正义 + 徽记，每局 12.2 点）。bot 内战里 120 个对局方只超进化过 1 次班德奈特、进化正义 24 次，伤害主要靠相枛津疾驰（7.2 点），多数第 10 回合以后才分出胜负。玩家的露莉亚第 6 回合才打（增幅 8：抽一张 7 费以上随从、回 7 费），bot 第 3～4 回合就当 2 费 1/1 打掉。
  - 原因之一是评估的 bug：两套评估都把主战者区域的徽记算成持有者的加分（学到的模型也学成了"对手有徽记对我不利"），给对手焦灰徽记就成了亏的。修正（`evaluate.crest_burn`、`effective_hp`）：在沙盒里量每个徽记每回合让持有者掉几点血（63 个徽记里只有焦灰徽记会，2 点），会伤害持有者的徽记按"`BURN_TURNS` 回合要掉的血"从持有者的血量里扣掉，不算加分。修好的 bot 对旧 bot 内战 72/120（60%），超进化班德奈特 48 次对 11 次。
  - 从玩家的 10 局学跳费龙内战的出牌时间（`learn/timing/ramp-ramp.json`），让 bot 按这个节奏出牌（`+pace`）：对不加的 59/120（49%），没有效果。局数太少，时间表太粗。
- **找"为什么这个节奏能赢"：反事实推演 + 假设验证**（玩家："让 bot 单纯学节奏是永远学不会的，要找到为什么我会是这个节奏，并且能赢 bot"）：
  - 反事实推演：玩家 10 局内战里，bot 从同一局面会打得不一样的 47 个回合，各从两种打法分岔，接下来都交给 bot 对 bot 打到终局（每岔 16 次，隐藏信息两边同样重抽）。玩家的打法平均只高 3.6%（更好 15 次、一样 18 次、更差 14 次），超进化班德奈特的回合单看甚至 -3%。单步决定接着交给 bot，计划就断了，价值显不出来：玩家赢在决定之间的配合（超进化班德奈特之后接着进化正义，徽记和正义一起烧血），不在单步。
  - 所以用"提出假设 → 让 bot 整局都按这个原因决策 → 和原版对打"来验证（都是跳费龙内战）：焦灰徽记是对手的持续扣血、还克制回血（修评估）60%，是真原因；照玩家的出牌时间表打（`+pace`）49%；增幅牌等到增幅（`search.moves.wasted_enhance`、竞技场 `+enhance`：沙盒量出增幅多值多少，露莉亚 3.5、宣扬的龙人 2、世界的呈现 2、佐伊 0，值得等而且两回合内够费就先留着）51%。露莉亚晚打只是表面，不是赢的原因。
- **评分修正和训练**（玩家："bot 最大的问题是评分机制"；照分析修评分，用现有对局训练）：
  - 诊断（只分析不改代码的那一轮）：bot 的评分预测内战胜负的 AUC 第 3～4 回合只有 0.54～0.55，第 5～8 回合 0.62～0.70，和"血量差 + 场面攻防"差不多；它学自"跳费龙对破魔虫"的对局（龙赢 88%），带着"我是跳费龙所以赢"的大常数，在玩家的内战里双方同时"看好自己"；玩家和 bot 打法不同的 47 个回合，它 37 次偏向 bot 的打法。结构上：只是快照里的总量相减、只数数量不看内容、看不到对手回应和以后、学自错误的对局、血量当分数而不是资源。
  - 第二版特征（`learn/roles.py`，`features` version 2）：沙盒量出每张牌打出来的作用（打脸、解场、回血、过牌、跳费、身材）和场上每轮自己生效的效果（打脸、回血、清场：正义未进化回 8、清 2 个，进化后打脸 8）；每边加上手牌的作用（对手的按没见过的牌里它手牌所占的份额估，也就是记牌）、牌库里剩下的作用、场上每轮的效果、主战者能撑几回合。
  - 同一批检验对局上：内战预测 AUC 旧模型 0.641、新特征 0.761，跳费龙对破魔虫 0.741 对 0.831；认出玩家每一步的选择 52% 对 59%，整回合 27% 对 41%（按局留出）。
  - 但预测准不等于下得强：完整新特征的 bot 对旧 bot 内战只有 32%。我方的库存特征（手牌作用、牌库剩余）让搜索攒着不出：每局进化 2.1 次对 3.3 次、出牌 8.5 张对 9.8 张。加重玩家选择（λ=5 / 20）38% / 34%，去掉进化点、手牌数、PP 上限 31%，在旧模型上学修正 38%。只去掉我方库存特征（"安全版"）：内战 AUC 0.774，对旧 bot 62%。安全版再加上玩家选择又掉到 30%：单回合搜索学到"留资源"，却没有玩家留资源要配合的后续计划。完整新特征最"像玩家"（47 个回合里 34 次偏向玩家的打法），实战却最弱。
  - 混合两种对局训练的安全版打破魔虫 AI 变弱（90% 对 96%），所以按对局分模型（`Learned` 先找 `<职业>-<对手职业>.json`）：内战专用模型（只用内战数据）对旧 bot 61%；用它再自我对局一轮重训（`tools/train_matchup.py`），对旧 bot 60%、对第一轮 52%，到顶了，装成 `learn/weights/dragon-dragon.json`；打破魔虫等其他对局照旧用 `dragon.json`。装好后从默认 bot 再核对一次：对只有旧模型的 bot 内战 113/160（71%）。
- **让 bot 自己找胜率更高的计划**（玩家："bot 只知道怎么赢，不知道怎么做手牌和轮次规划，拿到的不是特别好的牌就不知道怎么打了"；"希望 bot 自己找到胜率更高的计划，而不是跟着我的计划走"）：
  - 计划老师（草稿脚本）：从新 bot 自我内战的回合开始处，列出这回合几种用手牌的办法：bot 自己的打法；它打出的每张牌各留一回合；不进化、不超进化；它没打的牌先打（最贵的两张）；直接结束回合。每种都由同一个搜索（`mcts:60+plan+learned`，用 `veto` 禁掉别的选择）打完这回合，然后两边交给快 bot（贪心 + 便宜的斩杀检测，一局约 0.7 秒）打到终局 12 次，隐藏信息每种计划同样重抽。513 个局面，没有用玩家的任何打法。
  - 发现：bot 自己的打法大多就是这些办法里最好的（留一张、提前打一张、不进化平均都更差，直接结束回合差得最多）；约四分之一的局面有别的办法高 10% 以上。评分和老师意见相反（老师差距 > 15%，不算结束回合）的有 219/800 对，抽 60 对每种计划重新洗牌各打 24 局：老师仍对 37 对、反过来 18 对、打平 5 对，第一次平均差 +27.5%，重测 +12.1%。所以评分确实漏看了东西（什么时候放大随从、什么时候跳费、这回合超进化反而亏），老师自己能找出来。
  - 但把老师学进评分没有变强（跳费龙内战，对装着的模型，`mcts:100+plan+learned`，各 100 局）：排序损失（同一局面两种计划胜率差 > 10% 的配对）、把每种计划的胜率当软标签（连没选的计划也算：自对弈胜负只见过 bot 选了的局面），看或不看我方库存特征，线性 44% / 44%；加一层 16 个单元的隐藏层（`LinearValue` 的 `hidden`）留出排序从 0.857 到 0.879、不算结束回合从 0.759 到 0.821，实战却只有 22%（只在回合结束的局面上学，搜索在回合中间的局面上打分时乱外推）。
  - 关键检验：直接在对局里用老师挑计划（每种计划 8 次推演，先在重新洗过的局面上做计划，不偷看牌库）对 bot：51/100，35% 的回合换了打法，没有赢得更多。老师的推演是贪心快 bot 打的，判断并不比带搜索的 bot 强：教不出比自己强的学生。这和自我内战里起手好坏几乎不影响胜负（51% 对 49%）一致：双方都不会把资源变成胜势，也都不惩罚对方浪费资源，玩家会。
  - 换更强的老师：推演改由搜索 bot（`mcts:20+plan+learned`）两边对打，只有比 bot 自己的打法高出 1/8 以上才换：55/100（±10%，还在误差里），37% 的回合仍然换了打法。单回合的换法里，bot 对自己已经差不多是最好的；玩家赢在跨回合的配合（这回合留正义、下回合配超进化），而推演里留下的牌下回合怎么用全凭 bot 临时决定，留牌背后的计划根本没被推演出来。下一步：两回合计划（留下的牌下回合先打、没用的超进化下回合用），推演时下回合照计划执行。

- **跨回合规划，第一轮**（设计文档阶段 2，`agents/crossturn_agent.py`，`+cross…`；进行中）：
  - 做法：每个自己回合的第一个决策先照常搜索，读出树上的主线（每层访问最多的走法）。候选 = 主线，加主线配一个本回合限制：留它打出的某张牌（keep:卡号）、留额外 PP（save）、不进化（noevo）。每个候选在 K 个确定化上推演（所有候选同一批）：打完这回合，对手回合用策略头（`learn/policies/ramp-ramp.npz`，拟合自 v1 自对弈的访问分布）首选，然后打分，取平均（不取最大）。最好的限制要胜过主线（超过 margin 和 z 倍配对标准误），才挂到搜索的 veto 上管完整个回合；否则这回合完全是基础搜索。
  - 打分三种：`cross` 在下回合开始用 ACT 模型（便宜版）；`crossn` 再用策略头打完我方下回合，用 ENDED 打分（贵版，留下的牌下回合能用掉）；`crosss` 是对照，只用本回合结束的 ENDED、不推演。`rN` 让限制候选的本回合打法来自该限制下 N 次迭代的重新搜索，而不是主线去掉受限走法再补完。测量函数 `keep_value(state, player, uid)` 和自对弈 / 评测台记录（`record["plans"]`，评测台写到 `<out>.records.jsonl`）共用同一套候选。

- **CR（职业积分）**（`learn/rating.py`、`tools/cr.py`，规则由玩家给出）：
  - 规则：进入 GM 时按分组定底分，钻石 1600、蓝宝石 1550、红宝石 1500（更低的分组不算）；只和 CR 相差 200 以内的对手匹配；差距 = 我的 CR − 对方的 CR，赢了 +(16 − 差距/25)，输了 −(16 + 差距/25)，一方得多少另一方失多少；高出 175 以上赢只加 8、输扣 24（反过来低 175 以上赢加 24、输扣 8）。规则没说怎么取整，`change` 四舍五入，估算时用精确值。
  - CR 的含义：CR 停在期望涨跌为 0 的地方。差距 175 以内，稳定时的胜率 = 50% + 差距/800：高 80 分对应 60%，高 175 分对应 72%；对所有够得着的对手都赢 75% 以上，就会一直涨到谁都匹配不到为止，规则从此分不出强多少。
  - 估算：所有参与者（AI 的各个版本、玩家）从基准的 CR 出发，按两两胜率反复施加期望涨跌，直到不再变化，相当于“大家在天梯上互相匹配”最后停下的位置；90% 区间是把每一对的胜率按局数允许的范围重新抽样再算。基准是玩家（告诉我们真实 CR 后就是绝对值，否则读作和玩家的差）。
  - 局数和精度：胜率在一半左右时，90% 把握测准到 ±90 分要约 54 局，±50 分要约 174 局；5 局只能定到 ±300 左右。所以 AI 之间的差距用大量 AI 对局来测，玩家的对局主要用来把整张表钉到人类的刻度上。

- **斩杀潜力和规划器提方案**（第 1 层实验，通用、不针对卡组）：
  - 评估函数可选加一项"下回合最多能打多少"（`Weights.setup`、`setup_lethal`，`combo.next_turn_damage`：把局面投影到下回合开始，PP +1、连击清零、随从都能攻击、抽到的牌算未知，交给规划器算，300 节点预算加缓存，每次约 4 毫秒）。默认不开，`+threat` 开启；`+hand` 只算手牌和护符，因为场上随从多半会在对手回合被处理掉；
  - 规划器提方案（`LethalAgent(macro=True)`，`+macro`）：不能斩杀的回合也让规划器给出"这回合最多能打多少"的路线，照着打完再结束回合的局面用 MCTS 自己的评估打分，比 MCTS 的最佳一步高就照着打。原因：破魔虫的连招要连续走 6～10 步才兑现伤害，MCTS 每步 200 次模拟看不到那么深。
  - 实测（破魔虫一方换不同的 AI，跳费龙一方固定为 `mcts:200+plan`，同一批种子先后手各半，每组 200 局）：

    | 破魔虫一方 | 胜率 |
    |---|---|
    | `mcts:200+plan` | 14% |
    | `+threat` | 18% |
    | `+hand` | 18% |
    | `+macro` | 16% |
    | `+macro+hand` | 22% |

    方向对，但差距都在误差附近，离高手的 60% 以上（玩家的判断）还很远。所以下一步不再盲目调权重，而是让玩家用破魔虫打 10 局，用复盘工具找出 AI 和高手的分歧在哪里，再决定算法。
- **调权重**：用贪心智能体自对弈（每个候选 600 局，海盗 vs 龙）逐个试 16 个权重各 ×1.6 和 ×0.6，没有一个能稳定赢过原权重（42%–52%，门槛 55%）。手设权重已经在附近的最优点，要再提升得改评估的结构，或者换成学出来的价值网络。
- **预判对手的回合**（`reply=True`，竞技场里叫 `mcts-reply:N`）：在"结束回合"的叶子上，让贪心智能体拿着确定化出来的手牌替对手打完一个回合，到自己下回合开始时再打分。实测和不预判的版本 51% : 49%（100 局），没有可测出的提升，每步用时却从 65 毫秒涨到 481 毫秒，所以默认关闭。贪心对手太粗糙，模拟出来的对手回合信息量不大。
- **结论和下一步**：在"人工评估 + 搜索"这个框架里，多搜、调权重、模拟对手都没有明显提升，瓶颈是评估函数本身。下一步是用自对弈数据训练价值网络（以及给搜索排序用的策略网络）替换人工评估（§9.3），搜索框架不用变。这需要大量对局，引擎速度会成为瓶颈（§11）。
- **规则一致性**：AI、斩杀求解器、练习题用的是同一个引擎，所以它们的结论在规则上一致。

### 9.3 Gym 环境与强化学习（后期）
- **观测编码**：手牌 9 个位置、双方战场各 5 个位置、两个主战者，每个位置一个特征向量，包括 card_id 嵌入（封闭词表）、费用、攻击力、生命值、关键词位、进化状态；再加上 PP、EP、SEP、回合数等全局特征。
- **动作编码**：行动类型 → 来源位置 → 目标位置，每一段都配合法动作掩码。思路和 Jason 项目里的（卡槽, y, x）一样。
- **训练经验**，来自 Jason 的视频：
  - 先用最简单的网络；
  - 训练时盯着 `approx_kl`、`clip_fraction` 和熵；
  - 慎用奖励塑形；
  - 对手按"随机 → 规则型 → 历史版本自对弈"的顺序逐步加强。
- **更推荐的方向**：AlphaZero 式的"价值网络 + 搜索"。SWB-RL 的结果已经说明，纯 PPO 很难练出强战术。

## 10. 手牌条件价值（占位，架构会话的方案 docs/hand-value-design.md，claude/bot-architecture-design 24e9165）
玩家 2026-10-07 的方向：让 bot 自己评估不同卡组的不同手牌在不同条件下的价值，以此为导向训练。硬约束不变：没有按卡牌定的固定分（§9.2 开头）。还没有代码，这里只定接口：
- **学生** H(手牌 | 局面)：给整手牌定价。每张手牌 = 卡牌嵌入 + `learn/roles.py` 的功能向量 + 费用 + 下回合能否打出 + 还差几回合；局面 = 回合、当前 / 下回合 PP、双方血量、场面摘要、我方剩余进化 / 超进化点、对手未见牌的功能份额（`op_hand_*`）、双方牌组大小、双方卡组。每张牌的编码先和局面拼接过一层，再集合汇聚（DeepSets 或一层小 attention）。卡牌嵌入不能直通输出，只能经局面门控后才有贡献（结构保证"没有固定分"）；单元测试用玩家的例子：9 费后手里 9 张妖精 vs 「安娜题码 + 正义」两张，后者必须更高，同一张牌 2 费和 9 费时的边际价值必须不同。
- **训练目标**是差分：H(手牌) − H(手牌 ∖ {c}) ≈ T(c | 局面)，T 由测试会话的配对终局分支给出（G_end：有 c / 没 c 两条分支用同一套随机数、同一牌序，由当前 bot 打到终局）。所以自对弈记录要能复现：`netdata._identity` 存的种子、每回合开始的手牌和牌组（§9.2 "比赛卡组导入"）。
- **键**：编码器全卡池共享，卡组只经局面门控进入；线性底座（ENDED / ACT）照旧按对局分开（`learn.model.matchup_keys` 的键和回退），每个对局 1500 局自对弈以上才微调最后一层。
- **接入**：H 作为 ENDED 的加项（像 `learn/net.py` 在线性模型之上学修正），只对根节点就在手里的牌算（`mcts._root_deck`），本回合抽到的牌用"未知牌"取牌库平均；Σ 替代 `me_hand` 张数，张数留作对照特征。
- **过门**：学生先过"单元测试 + 玩家 80 回合留牌 AUC ≥ 70%"才接入搜索；接入后和 (b) 分开过门，strong 档对 v2s 等算力，SPRT 后定长 600 局；自对弈每局打出牌数、进化次数不比 v2s 少 5% 以上。顺序：跳费龙镜像先做，每个新对局在它自己的 ENDED 拟合之后。

## 11. 性能
测量环境是单核 Python，随机对局：

| 指标 | 海盗皇家 vs 跳费龙 | 随机卡组（全卡池） |
|---|---|---|
| 完整对局 | 约 170 局/秒（约 1.2 万次行动/秒） | 约 140 局/秒 |

- **热点**：合法行动生成（`_play_actions`、`play_form`、同名手牌去重）占一半以上时间，其次是触发的入队和广播。
- **搜索的热点是 clone**：斩杀搜索每个节点都要复制局面。`CardInstance.copy` 从 `copy.copy` 改成逐字段赋值后快了约 10 倍，斩杀搜索整体快了约 2.7 倍；现在 clone 仍占搜索时间的一半左右，大头是复制牌组里的 30 多张牌。
- **优化顺序**：
  1. 牌组写时复制（牌组里的牌很少被改动）；
  2. 缓存每回合不变的部分（比如手牌的使用形态），减少重复计算；
  3. 还不够快，就把核心用 Rust（PyO3）重写，Python 接口保持不变。
- **原则**：每次优化之前都先用 profiler 找热点。

## 14. 待确认的规则问题
1. 超凡世界是否有回合上限（初代是第 40 回合双方判负）。引擎现在用 `max_turns` 兜底。
2. 进化点、超进化点被回复后能否超过 2；能否在解锁回合之前使用。
3. 融合是"每回合 1 次"，还是"每张带融合的牌每回合 1 次"（英文和日文描述不一致）。
4. 0 点伤害能否击破非超进化随从的屏障。引擎现在按"任何一次受伤事件都会击破"处理（依据：超进化随从受到 0 点伤害时屏障也会消失的 Q&A，以及"0 点伤害也算受到伤害"）。
5. 随机效果能否选中潜行随从。推测可以，因为限制写的是"被选择"。
6. 奥义里的"当前回合数"指全局回合数还是己方回合数。
7. 法术进入墓场的时机，是结算前还是结算后。引擎现在放在结算后。

### 已确认的卡牌细节
2026-10-05 由玩家确认，测试里都有对应用例：
- 黄金时代召唤的海盗旗，**不会**被这张黄金时代本身推进（反应在使用卡牌时就入队，见 §6.2）。
- 伊德梅塔进化时信仰值不足 5：**什么都不发生**，不扣信仰值，也不获得能力。日文原文是"信仰値を-5して、…を持つ"，按惯例这是一个要先付得起的消耗。
- 两张伊德梅塔都进化，"+1/+1"能力**会叠加**，之后每张爆能强化的牌给 +2/+2。
- 触发信仰"+1/+1"的那张爆能强化随从，自己**也能**吃到 +1/+1。

2026-10-05 第二批（全卡池），同样都有用例或注释：
- 纹章：转动的《命运之轮》·斯洛士在吟唱归零的那个回合，回合开始能力**照样发动**，3 个回合正好发动完 3 个效果。引擎在吟唱归零时先破坏纹章，所以这一次由它的谢幕曲完成（表里的近似处理）。
- 大游戏世界自己也算"战场上原始费用为 X 的其他卡牌"：场上有它时，每使用一张 1 费的卡都推进一次。
- 森林陷阱：进场的敌方随从在陷阱结算前已经离场、或者不会被破坏时，陷阱自己照样破坏。
- 天司长的继承者·圣德芬被瞬念召唤后被对手的森林陷阱破坏：**仍然获得纹章**（"被瞬念召唤时"在本卡离场后照样结算，只是无法返回手牌）。
- 从本局被破坏的卡里随机挑选时，**被破坏次数越多越容易被选中**（混沌监狱·阿兹弗特，以及崇高的天书、崇高的憎恶·康蒂玛、器械操纵者·吉尔克等）。
- 万食的安纳提玛·拉拉安瑟姆进化时没有敌方随从可选，**仍然进行土之秘术**。
- 超进化随从受到 0 点伤害时屏障也会消失；引擎按"任何一次受伤事件都会击破屏障"实现。
- 以下按原先的实现确认：巴别隆城空手启动仍推迟吟唱值；进化的 +2/+2 算获得增益（露芙蕾、蒂亚）；慈惠的心腹包括自己的进化；丘比丹计量 ≥15 时奥义和解放奥义都发动；卡婕、卡特斯罗特纹章的"每回合一次"（前者没目标也算用掉，后者只在真正进化时算）；罗德诺艾尔四世两档爆能强化叠加；希耶提包括自己；骁勇骑士的"最左边"是最早登场的；琳库露纹章可以把生命上限降到 0；赛菲满场融合仍扣 2 PP；波摇花的裁决的 X 按被销毁的牌的费用算；伊斯坦戴德 对 玛尔奇盖特纹章照样破坏敌方随从；莉迪耶尔的自伤在模式之后；审理的守卫、天书深渊、艾尔拉德纹章按英文的条件理解；索菲娜沿用拉姆蕾达的 Q&A；回复 0 点也触发"回复时"；锻磨保镖没目标也回复；尤斯提斯没目标也进化。
