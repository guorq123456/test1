# +par=4 的门前读数（根并行 ISMCTS；没进任何档位）

**条件：**对手卡表已知（牌序、手牌未知）。

架构线程 2026-10-10 10:01Z 布置。机器是这个 4 核容器；每棵树一个 worker，主进程只合并。
代码：search/parallel.py（d413c0e），本次补了两处，默认行为不变：
- **gate 的修正**：`--workers 1` 时，对局改在本进程里下，不再进进程池。原因是进程池的 worker 是守护进程，不能再开子进程，+par 在 gate 里会直接报错。
  - 核对：同一组种子用 `--workers 1` 和 `--workers 2`，行逐行一样（去掉 ms 和 cpu）。
  - **+par 的门必须用 `--workers 1`。**
- **调用脚本要有 `if __name__ == "__main__":` 保护**（spawn 方式会重新导入主脚本）。turn_cost.py 补上了保护。我第一次计时就因为缺这个，worker 不停重启，那次作废。
- 每步决策另记每棵树的 CPU（`last_tree_cpu`）。

## 1. 墙钟（turn_cost.py，第 1 步前 300 个开头，整回合，A/B 交替先跑）

| A | B | 每回合 ms（A / B） | ms A/B | 迭代 A/B |
|---|---|---|---|---|
| level-strong+par=4（每棵树 200） | level-strong | 370.5 / 285.7 | **1.297** | 3.963 |
| mcts:170+plan+learned+phased+par=4（每棵树 170） | level-strong | 336.4 / 304.7 | **1.104** | 3.341 |

- 目标 ≤ 1.15，每棵树 200 次迭代时**没达到**。
- 每棵树降到 170 次能达到，这时总迭代是 level-strong 的 3.34 倍。
- 两次跑的 level-strong 每回合差了 6%（285.7 / 304.7），这是机器本身的抖动。
- 进程池启动约 0.54 s，算在 A 的第一步里，平摊到 300 个开头约占 0.6%。

**开销拆开**（par_break.py，120 个开头，每个开头的第一步决策，单位是每步 ms）：

| 并行墙钟 | 每棵树 CPU 平均 | 每棵树 CPU 最大 | level-strong 墙钟 / CPU | 局面序列化 |
|---|---|---|---|---|
| 136.5 | 106.8 | 128.8 | 107.7 / 106.8 | 0.7 ms，13.8 KB |

- 每棵树的 CPU 和单树一样（106.8 对 106.8），4 核同时跑没有让单树变慢。
- **约 20 个百分点是等最慢的那棵树**：同样 200 次迭代，不同确定化下耗时不一样，最大值平均比均值多 22 ms。
- **约 7 个百分点是进程间来回**：发局面、收结果、合并。
- 能压开销的做法：
  - 少给每棵树一些迭代（上表的 170）；
  - 或者每棵树按时间停，但那样同一种子就不能复现了。
