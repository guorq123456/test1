## 2. 模拟器怎么跑

### 2.1 入口和一局的流程
- `engine.new_game(deck0, deck1, seed, first=None, max_turns=60)`：用 `random.Random(seed)` 建局。`first` 不给时由种子决定。先洗 0 号的牌、发起手，再洗 1 号的。
- 一局：`while not state.over: a = agent.act(state, legal_actions(state)); apply(state, a)`（agents/random_agent.py 的 play_game）。
- **智能体拿到的是完整的真实 GameState**，不是观察。见第 5 节。

### 2.2 动作空间
八种行动：换牌、使用手牌（目标和模式一并给出）、攻击、进化 / 超进化、启动护符、融合、额外能量点、结束回合。所有选择都折叠进行动里，结算中途不再问。一个决策点通常几个到几十个合法行动；完全相同的手牌只生成一组。

### 2.3 可观测状态
`view.observe(state, player)` 给：回合、行动方、双方生命 / 上限 / 伤害上限、PP、EP、SEP、牌库张数、墓场数、双方战场和主战者区域（每张牌的 uid、名字、费用、身材、关键词、计数），自己的手牌，对手的手牌张数。
**没有**：对手打出过、展示过的牌的历史（要从对局记录里自己攒）；对手职业不在 observe 里（在卡组里）。底座要补这两样。

### 2.4 克隆、回滚、确定性
- `state.clone()` 是完整独立的复制，默认连随机数状态一起复制；`clone(copy_rng=False)` 不复制随机数。没有回滚，要分支就先克隆。
- 引擎在给定种子和行动序列时是确定的（README、records.py 的设计，模糊测试也查同种子复现）。
- **跨机器的浮点不一定逐位一致**：见 9.4。重放检查要在同一台机器、同一个 Python 上做，日志里要记平台和版本。

### 2.5 单局耗时（云端容器）
默认打法 `mcts:100+plan` 对 `mcts:100+plan`，bot 冻结七副两两（有序对，各不相同），84 局，4 个进程，种子 99000000～99000083：

| 每局挂钟时间 | 平均 1.90 秒，中位 1.63，最长 4.29 |

### 2.6 多进程和 Salem 电脑上的每小时局数
- 多进程可以：现有工具都用 multiprocessing.Pool；每局独立，没有共享状态。
- svsim/tools/host.py 只做「低优先级 + 不占 CPU0 + 最多 12 进程」，**不会只用 E 核**。这次的工具要另外设 E 核掩码。

  | | 单进程（14 局，种子 99000100～113） | 11 个工作进程 + 1 个主进程 = 12（168 局，种子 99000200～367） |
  |---|---|---|
  | 每局决策数 | 69.8 | 65.6 |
  | 每局挂钟 | 1.54 秒 | 1.44 秒 |
  | 每局 CPU | 1.52 秒 | 1.35 秒 |
  | 每步 CPU 平均 | 21.8 ms | 20.5 ms |
  | 吞吐 | — | 实测 24941 局 / 小时（含进程池启动和收尾）；按单局平均推，稳定约 **2.76 万局 / 小时** |

- **「12 个进程」包括主进程**：Pool(12) 是 12 个工作进程加 1 个主进程，共 13 个，超限。所以工具一律最多 11 个工作进程。
- **Windows 上 `time.process_time()` 的精度只有 15.625 ms**（一个时钟周期），单步 CPU 时间的中位数、分位数都被取整成它的整数倍，不能用。平均值和整局 CPU 秒数可用。每步算力的比值要么按整局 CPU ÷ 决策数算，要么改用 `QueryThreadCycleTime`（CPU 周期数，精确）。这一条进阶段 1 的 runner。
- 测速时电脑上有别的程序在跑（游戏和 OneDrive 同步，约占整机 28%，在性能核上）。并行时每局 CPU / 挂钟 = 0.94，单进程 0.99。所以这组数是「有人在用电脑」时的数。
- 跨机器：容器（Python 3.13.18 / numpy 2.5.3）每步 CPU 平均 27 ms，电脑 E 核 21 ms，电脑一个 E 核比容器一个 vCPU 快约 1.3 倍。
- 阶段 1 基线天梯的实际吞吐（电脑，11-21 08:39～09:07Z，11 个工作进程，E 核、低于正常优先级）：10667 局用 1650 秒，**约 2.33 万局 / 小时**（含池子每局结算、匹配和写日志，都在主进程里串行做）。比测速的 2.76 万低约 15%。
- **Windows 上的三个坑**（11-21 阶段 1 跑电脑时碰到）：
  1. 输出重定向到文件时 Python 的 stdout 是 cp1252，打印中文就报错退出。阶段 1 第一次全量就停在这里（基线跑完、结果已存，打印时崩）。处理：启动文件设 `PYTHONUTF8=1`，脚本开头把 stdout / stderr 改成 UTF-8。容器里试跑时用 `PYTHONIOENCODING=cp1252` 模拟。
  2. 虚拟环境的 python.exe 只是个启动壳，会再起一个真正的解释器：11 个工作进程时实际是 13 个进程（偏差 D5）。处理：启动文件直接起真正的解释器，设 `__PYVENV_LAUNCHER__`（multiprocessing 给工作进程就是这么做的），并检查它确实认得虚拟环境。
  3. 每步算力在 Windows 上记的是 CPU 周期数（QueryThreadCycleTime），Linux 上是纳秒；同一台机器上算比值没问题，跨机器不能直接比。报告里每步用时用挂钟毫秒。

## 3. 配对是否成立

**成立**（实测，云端容器，analysis/ladder/tools/probe_hidden.py，种子 99000500～99000519、99000600、99000700～99001699）：
- 同一个种子、同样两副卡组，发牌和先后手完全相同，和双方用什么策略无关（20 个种子逐张比对）。
- 自己的发牌只取决于种子和自己的卡组，不受对手卡组影响（先洗 0 号、再洗 1 号）。但这只在「自己坐 0 号」时成立：坐 1 号时，自己的洗牌在随机数序列里排在对手之后，对手卡组张数不同会改变自己的发牌。检验工具要么固定被测方坐 0 号、用 `first` 参数控制先后手，要么把对手固定。规划的「一对」本来就是同一个对手，所以没问题。
- `first` 可以显式给，先后手可以精确各占一半。种子决定先后手时，1000 个种子里 0 号先手 48%。
- 开局之后，双方的不同决策会消耗不同的随机数，后面的随机效果就不再一致。这是正常的，「一对」只要求开局相同。

## 6. 时间和算力限制

### 6.1 模拟器里有的
- 每局：`max_turns = 60`，超过判平局（裁定 R-01，未决）。
- 每步：**没有任何时间或算力限制**。现有工具也不设超时。runner 要自己加（任务说明 §4.2：超时算造成方输）。

### 6.2 「每步算力上限 1.08 倍」怎么执行
默认打法自己的单步 CPU 时间就从十几毫秒到一秒多（2.5 节），不能逐步卡。按项目检验报告模板的口径：**同一批局面 / 对局上，平均每步 CPU 时间之比 ≤ 1.08**，另报 p90 之比。另设一个单步硬超时（例如默认打法实测最长值的 5 倍），只用来抓死循环，超了判负。这是假设 A5，见 DEVIATIONS.md。

### 6.3 预算粗估（按电脑实测 2.76 万局 / 小时推，**推断**）
假设：所有成员的打法都和默认打法一样快（玩家的打法最多慢 8%）；每期 5 个玩家都交满名额。

### 11.3 胜率差换 CR
- **按 §3 的规则推（精确）**：分差落在第 k 档（25k ≤ d < 25k + 25，k = 0～7）时，稳定胜率 = (16 + k) / 32：

  | 分差 | 赢 / 输 | 稳定胜率 |
  |---|---|---|
  | 0～24 | +16 / −16 | 50.000% |
  | 25～49 | +15 / −17 | 53.125% |
  | 50～74 | +14 / −18 | 56.250% |
  | 75～99 | +13 / −19 | 59.375% |
  | 100～124 | +12 / −20 | 62.500% |
  | 125～149 | +11 / −21 | 65.625% |
  | 150～174 | +10 / −22 | 68.750% |
  | 175 | +9 / −23 | 71.875% |
  | > 175 | +8 / −24 | 75% |

  每档 25 分对 3.125 个百分点，**平均 1 个百分点合 8 CR，台阶状**。胜率落在两档之间时，分差停在两档的交界处。
- **加上每局加减分的噪声（推断，模拟）**：两个成员只和对方打、胜率固定，40 万局模拟（analysis/ladder/tools/cr_sim.py，随机种子 20261121）：胜率 51%～65% 时平均分差约合 **9.0 CR / 百分点**（例如 60% → 平均分差 89），68% 合 10.1，70% 合 11.1，72% 以上发散。分差本身的标准差约 86 CR。也就是说，台阶被噪声磨平了，但平均分差比「8 CR / 百分点」系统性地多出约 10 分（相当于每档中点）。
- 对阶段 1 的影响：「已知强弱检查」里，把直接对打的胜率换成预期分差时，要用池子实际的匹配方式做同样的模拟，不能直接乘 8。
