## M2：铺垫，Salem 对 bot（P_NL）

**量什么**：回合末的 P_NL = 我方下回合有斩杀的概率。
- 用建造线的 `next_lethal_prob(state, k, seed, reply_spec="level-strong")`：
  - 对手在 k 个确定化上用 `level-strong` 打完它的回合；
  - 然后在我方下回合开头跑 `find_lethal`；
  - sure 记 1。
- 细节（建造线 02:33Z 确认，在任何运行之前）：
  - 模块 `svsim/search/foresight.py`。
  - 传入的是我方 `EndTurn` 已经由引擎执行的局面（默认 `opponent_started=True`）：对手的回合开始（含抽牌）已经跑过，同记录里一样；「我方」= 1 − state.active。
  - 确定化从我方视角：对手手牌和牌库合成一池、双方牌库顺序、随机数重设。k 个样本和回复 agent 的种子都由 `seed` 确定地派生；两条线传同一个 seed，确定化的种子就相同。
  - 我方下回合开头照引擎抽牌，再用默认参数跑 `find_lethal`；sure 记 1，其他记 0（不用 probability）。
  - 对手回合里我方被打死记 0；对手回合里我方赢了（对手抽空牌库、效果等）记 1。
  - 返回平均、每个样本的值、`find_lethal` 没跑完的次数、每个样本的结束方式和耗时。没跑完的次数照报。
  - 建造线提供的两个省时开关（`nodes` 改节点上限、`planner_first` 规划器先验）都不用，照默认参数。

## M4：按方向打到终局（建造线写工具；分析线读）

**做法**
- 从 M3 那 85 个开头的两个回合末（Salem 的线、bot 的线）出发，各打到终局 K 次：
  - 我方在剩下的整局里一直照一个方向走；
  - 对手用 bot 走（具体见下）。
- **方向**：候选风格的多回合版本，由建造线写成工具：
  - race：斩杀时钟；
  - clear：新写；
  - conserve：keep / save；
  - default：不加方向。
- 一条线的分数 = 各方向胜率的最大值；取到最大的那个方向就是这条线选的方向（打平时按 default、race、clear、conserve 的顺序取前一个）。
- 每局都从回合末重新确定化隐藏信息（我方视角），每局一个种子。同一开头的两条线、四个方向用同一批 K 个种子（配对）。

**参数**（分析线定）
- **打到终局用的 agent**：对手和各方向底下的搜索都用第 0 步 G_end 的 bot `mcts:100+plan+learned+phased`，和第 0 步的 G_end 一致，也比 `level-strong` 省一半。
- **K = 12**：85 × 2 × 4 × 12 = 8160 局。按 G_end 每局约 2.8 CPU 秒、方向策略再加约五成算，约 3.4 万进程秒，RC 12 进程约 50 分钟。
  - 建造线的工具冒烟以后，如果估计超过 75 分钟，改用 K = 8，在运行之前标出来。
- **种子**：第 i 个开头（85 个按第 0 步的 k 排，i = 0～84）用 **66540000 + 500 i**，由工具派生每局的种子。

**报什么**（读法写在任何运行之前）
- 分数偏向 Salem 的比例：Salem 的分数严格更高算 1，相等算一半。
- **配对差**：每个开头「分数偏向 Salem」减「T 偏向 Salem」，平均和区间（按开头重抽 2000 次，种子 0）。
- 和第 0 步 G_end 胜者的一致率：两者都不打平的开头上，偏向同一边的比例。
- 两条线各方向的平均胜率；选中方向的分布；和 M3 归类的交叉表。
- **J32**（架构线程）：在这 85 个回合上，这个分数偏向 Salem 的比例高于 T 的 54.1%，置信 55%。看点估计。

**要先写下的局限**（架构线程）
- 在有噪声的估计上取最大，会往上偏；两条线偏得一样多。
- 整局固定一个方向很粗糙，真人会中途换方向。
- 对手策略是 bot。

## 补充（02:4xZ，建造线 dcb9159 / d7aa1ad 推上来之后、任何冒烟和运行之前）

**M2**（架构线程 02:48Z 的两条，加上工具的实际接口）

**M4**（工具的实际做法，d7aa1ad）
- `direction_rollout(state, "all", k, seed, opp_spec, our_spec, nodes)`：
  - default 就是 `our_spec` 本身；
  - race、clear、conserve 每回合用整回合规划器（`search.turnplan`，每个计划 `nodes` 个节点、2 个样本），外面套斩杀 agent（有斩杀一定打）；

- `our_spec = opp_spec = "mcts:100+plan+learned+phased"`（同上）。
- **`nodes` 的定法**（冒烟定，不看任何结果）：
  - 冒烟在 2 个开头上量四个方向每个我方回合的毫秒数；
  - 从 {100, 150, 200, 300, 500} 里挑一个，让三个带方向的平均每回合耗时最接近 default 的；
  - 不同方向的算力不一样，取最大时会偏向算力多的方向，所以先配平。
- 冒烟用库外种子 99600000 起。

  - 纯 conserve 那 30 个里，T 和 G_end 都只是一半对一半：光是「留着」，按这两把尺子看不出赢面。
  - 偏向 Salem 的集中在 mixed（31 个，两把尺子都是 71%），也就是 Salem 在同一回合里同时多做了两件事（多铺场又多留资源、多打脸又多留资源）。这更像 bot 在这些回合**用资源的效率低**，而不是选错了大方向。
  - 纯 race、clear、develop 都只有 2～6 个，太少，不读。
- **局限**：阈值是事先拍的，类别的边界粗；只用了通用字段，不知道留下的是哪张牌；85 个开头分到 7 类，每类都小，比例没有区间，不当结论用。setup 那一版等 M2。
