# 根并行 `+par=k` 的门：等墙钟、不等 CPU（架构线程 2026-10-10 10:01Z 布置；写在候选做出来、任何门的对局之前）

**条件**：对手卡表已知（牌序、手牌未知）。

**候选**（建造线拆完 329、455 之后做；目录名、提交号、智能体串、`k` 怎么并行，开门前补在这里）
- `+par=k`：k 棵独立的树，根节点合并访问次数。
- 每一步的墙钟和单树差不多，CPU 是 k 倍。

## 这道门和以往不同：**等墙钟，不等 CPU**

- 以往的门都按 CPU 配平（每搜索决策毫秒，单进程里墙钟 ≈ CPU）。这道门比的是**同样的响应时间**：A 可以多用 CPU，只要每一步的墙钟和 B 一样。
- 所以结论只适用于对局时手边有 k 个空闲 CPU 的机器（例如 Salem 的机器）。CPU 紧张时不成立。

## 门

- **A** = `level-strong+par=4`（建造线给的串）；**B** = `level-strong`，即 `mcts:N_B+plan+learned+phased`，N_B = 200 起。
- **原版跳费龙镜像**直接对打，`--fixed --max 600`，**定长 300 对**，种子 **67400000～67400299**。
- **机器的用法**（和以往不同，写在这里）：
  - A 每一步要同时用 4 个 CPU，所以门**一次只打一局**（`--workers 1`）。
  - 不经 `svsim.tools.host`：它会把进程挪离 CPU0，只剩 3 个 CPU。改用 `nice -n 10 python -m svsim.tools.gate …`，让单局可以用容器的全部 4 个 CPU。
  - 门跑的时候容器里不跑别的。
  - 不进 CPU0 是 Salem 机器的规矩，这里是分析线自己的容器。
- **等墙钟复核**（在门之前）：
  - 门命令 `--fixed --max 40`，`--workers 1`，20 对，种子 67499000～67499019，看门自己的「每搜索决策毫秒」A ÷ B。门是在主进程里用 `perf_counter` 计时，量的是墙钟。
  - 同时用 `turn_cost.py --n 300`（单进程，墙钟）量第 1 步前 300 个训练开头的整回合墙钟 A ÷ B。
  - 两个比值相差 3 个百分点以上，用整回合的。用的那个比值在 0.97～1.03 之外，就修一次 N_B = round(200 × 比值)，不再复核。
- **A 每步实际用的 CPU**（照报，不进判定）：
  - 优先用候选自己记的每个决策 k 棵树的 CPU 秒合计。
  - 候选不记的话，在整回合计时里另量：同一回合里 A 的墙钟毫秒，和 CPU 毫秒（主进程加子进程，`os.times()`）。
  - 报「A 的 CPU ÷ A 的墙钟」和「A 的 CPU ÷ B 的 CPU」。
- **判定**：单门规矩 (S)，`pooled.py` 逐对重抽 4000 次的下沿 > 50%。没有确认门。装机要 Salem 本人的话。
- **过的概率**（跳费龙镜像的对分标准误按以往门取 1.4～1.75 个百分点）：真实效果 0 / +1 / +3 / +5 个百分点时，约 2.5% / 8%～11% / 40%～57% / 85%～95%。
  - 参考：同样按 CPU 配平时 `mcts:1043` 对 `level-strong` 是 56.5%（拆分测量）。4 棵 200 次的树合并，大致在 200 和 800 之间。
- **J53**（架构线程）：`level-strong+par=4` 对 `level-strong`，按墙钟配平，过 (S) 门，置信 **55%**。
- **在哪里跑**：分析线的容器，一次一局，排在 `+abs0` 的门之后。估计 300 对约 40～60 分钟，外加复核约 15 分钟。
- **照报**：A 先手 / 后手的分数；两局走法完全相同的对数；门的墙钟毫秒比；复核的两个比值和最终的 N_B；A 的 CPU 读数。
